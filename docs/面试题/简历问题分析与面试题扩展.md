### 第 2 题：KnowOcean 架构（总→分→我）

KnowOcean 是一个企业级 RAG 知识库平台，核心是让用户上传文档后用自然语言做智能问答。整体分三层：前端 Vue 3 + Element Plus 的 SPA，后端 Python FastAPI 提供 REST API 和 SSE 流式接口，AI 链路走「文档上传 → ETL 解析切块 → 双通道入库 → RAG 检索增强生成 → SSE 流式返回」。

我沿着一条核心链路讲。第一步文档上传与 ETL：前端分片上传，后端 SHA-256 去重存文件存储，走异步 ETL Pipeline——读取 → 解析（PDF/DOCX/Markdown/TXT）→ 文本清洗 → 结构化切块，target 240 token、overlap 32 token，按段落边界切，语义完整性比固定窗口好很多。

第二步双通道入库：切好的块并行走两条路——调 DashScope text-embedding-v3 向量化进 PGVector 建 HNSW 索引，另一条进 ES 用 IK 分词建倒排索引。metadata 保留 source_doc_id、page_number、chunk_index 供引文标注。

第三步 RAG 问答：用户提问 → Query Planning（LLM 判断直接检索/改写/拆解）→ 双通道混合检索（PGVector 余弦相似度 + ES BM25，各取 Top 50）→ RRF 融合排序（k=0，偏向两通道都排前面的结果，实验效果比 k=60 精度高 8% 左右）→ cluster 聚合 + 邻居窗口扩展 → 4 级证据评估 → LLM 生成带结构化引文 → SSE 流式推到前端，Agent 推理过程实时可视化。

我的贡献：独立开发者，完整架构设计 + 全部代码实现。最核心的是混合检索引擎 + RRF 融合策略、ReAct Agent 推理链路、多轮记忆体系。

**追问 2.1：SSE 和 WebSocket 为什么选 SSE？**

三点。场景匹配：我只需要服务端推客户端，不需要双向——SSE 的单向推送够了。实现成本：SSE 是 HTTP 扩展，Nginx 默认支持不需要额外配置，浏览器原生 EventSource API 就能消费；WebSocket 需要协议升级、连接管理、心跳保活，工程复杂度高很多。调试友好：SSE 走普通 HTTP，curl 和 DevTools 能直接看数据流。SSE 的浏览器同域名 6 连接限制在知识库问答场景不构成瓶颈——一个用户同时只有一个对话。

**追问 2.2：ES 和 PGVector 查询是串行还是并行？**

并行。用 asyncio.gather 同时发两个查询，总延迟 ≈ max(PGVector, ES)。线上 PGVector HNSW 索引约 20-50ms，ES BM25 约 10-30ms，并行后检索层延迟控制在 50ms 内。

**追问 2.3：RRF 的 k 值为什么选 0？**

RRF 公式 score(d) = Σ 1/(k + rank(d))。k 越大排名差异越平滑，论文推荐 k=60。我选了 k=0，原因是在我的测试集上 PGVector 和 ES 在短查询场景表现差异大——PGVector 经常把第 1-3 名高相关文档排到前面，ES 关键词匹配的热度高文档可能只有中等相关性。k=60 会抹平这种差距，融合后高质量结果被稀释。k=0 更信任"两通道都排前面"的结果，牺牲一些多样性换精度。这个选择是基于实际测试数据集的，不是我编的。

### 第 3 题：从 Java 转 AI

这个转变不是突然转行，而是两条线并行。上家公司同时有电商和 AI 两条业务线，我主动申请参与 AI 知识库项目。因为在做电商时发现用户咨询、运营反馈、售后记录都是非结构化文本，传统 SQL 处理不了。RAG 恰好能把这些文本"激活"成可问答的知识——这是后端工程师能力的新出口。所以不是放弃微服务，而是把微服务治理、缓存、高并发的经验平移到 AI 工程化上。

怎么快速掌握这套技术栈？三个方法。一是任务驱动学——直接定下"做一个能用的知识库"的目标，遇到问题再查，多轮对话记不住就去研究记忆模块，检索不准就去学 RRF。效率比纯啃文档高很多。二是类比迁移——我发现 RAG 检索 ≈ 多级缓存+索引设计，Agent 规划 ≈ 状态机+策略模式，Embedding ≈ 特征工程+倒排索引，用后端思维理解 AI 上手很快。三是动手写并开源——整个 KnowOcean 放 GitHub 上，强制写能跑通的工程，踩了异步流式返回、SSE 推送、分块调优等大量坑，这些只有写出来才能真懂。大概 2-3 个月业余时间加上公司项目锻炼就基本掌握了。

**追问 3.1：后端转 AI 最大的思维转变是什么？**

三个转变。第一，从「确定性」到「概率性」——后端接口 100 次返回一样，LLM 100 次可能有 100 种回答，你要学会用 prompt、温度、Few-shot 控制输出可靠性。第二，从「单点优化」到「端到端评估」——后端看接口 RT 和 QPS，RAG 要看检索召回率、答案准确性、幻觉率，中间某环节优化了不代表最终效果更好。第三，从「接口设计」到「Prompt 设计」——以前设计 API 参数和返回值，现在设计 system prompt、tool description、Few-shot examples，这些 prompt 的准确性和稳定性决定了 Agent 的行为。

### 第 4 题：短查询召回

短查询确实对语义检索和关键词匹配都不友好。我们设计四层处理。

第一层预处理——Query Planning。Query Rewrite 把"退货政策"补全为"商品的退货政策是什么"，Multi-Query Expansion 生成同义变体并发检索融合，Query Decomposition 对"退货政策和配送时间"这种复合短查询拆成两个子查询。

第二层短查询召回策略。检测 ≤3 个词且无明显实体时，提高 ES match_phrase 权重、降低 PGVector 相似度阈值、引入 HyDE——让 LLM 先生成伪文档再用伪文档做向量检索。HyDE 增加 0.5-1 秒延迟，我们只对短查询且首次检索相关性低于阈值时才触发，约 30% 的短查询走 HyDE。配合意图映射表和高频缓存，大部分短查询直接命中。

第三层业务规则层。高频短词 → 标准查询映射表。"退货政策"定向检索 policy_return 标签，"免邮"映射 shipping_free。支持运营配置和日志自动挖掘。

第四层兜底。返回澄清问题——"您想了解退货的期限、运费还是流程？"，同时记录失败 query 用于后续优化。

**追问 4.1：意图映射表怎么维护？**

运营后台配置 `{short_query, target_tags, search_weight}`。自动化流程：每天分析 search log 中"查询量高但用户点了澄清问题"的 query，推给运营确认后自动加入。

**追问 4.2：HyDE 生成的伪文档质量差会带偏检索吗？**

会的，这是最早踩的坑。我们做了 HyDE 质量检测——把伪文档和原始 query 做 cosine similarity，低于阈值就丢弃 HyDE 结果，降级为纯关键词检索 + 澄清问题。

**追问 4.3：ES 里 match_phrase 具体怎么配置？**

用一个 bool query，should 里放三个：match_phrase on content boost=3（要求词连续，精度高权重最高）、match on content boost=1（兜底）、match on title boost=2（标题匹配权重高于正文 match）。具体 boost 值经过几次线上调参确定。

### 第 5 题：ReAct Agent 原理（★ 官方正确答案版）

ReAct 的全称是 Reasoning + Acting，核心思想是让 LLM 在推理过程中交替进行「思考」和「行动」，而不是一次性生成最终答案。

我举个具体例子讲循环。用户问"KnowOcean 支持哪些文件格式？"第一轮：Thought 判断这是产品功能问题，需要查知识库。Action 调用 kb_search("支持的文件格式")。Observation 返回三条结果，其中一条明确写了"支持 PDF、DOCX、Markdown、TXT"。第二轮：Thought 判断信息够了，输出 Final Answer。循环的本质是 LLM 每次先判断"我还缺什么信息？需要调什么工具？"，拿到结果后再判断"现在够不够回答？"，不够继续，够了结束。

和 Sequential Chain 的核心区别在于执行路径由谁决定。Chain 的路径是开发者预设的——"先调 A→结果传 B→再传 C"，无论中间数据是什么都走这条固定路线，就像工厂流水线。Agent 的路径是 LLM 运行时动态决定的，调哪个工具、下一步做什么都是基于当前状态实时判断的，可能两步够也可能要五步。具体差异：灵活性上 Chain 固定 Agent 动态，适用场景上 Chain 适合步骤确定流程 Agent 适合开放式任务，成本与可靠性上 Chain 调用次数确定成本可控 Agent 不确定 token 消耗更高。

选型标准很简单——如果你在写代码时无法预先列出一个固定步骤列表，就该用 Agent。流程固定的（文档上传→解析→入库）用 Chain，任务开放的（分析财报写投资建议）用 Agent。

终止控制三层：最大步数 5 轮、Token 预算超 4000 中断、LLM 置信度判断——连续两轮没提升就提前终止。还有一个去重检测：连续两轮相同工具 + 相同参数，提示换查询方式。

**追问 5.1：ReAct 最大的工程挑战？**

Prompt 设计。让 LLM 稳定输出可解析的 Thought-Action-Observation 格式，同时 Action 参数必须精确匹配 tool schema，这比代码逻辑本身难得多。我踩过的坑：LLM 跳过 Thought 直接出 Action、Action 的 JSON 格式不对、编造不存在的工具名。经验：工具描述要像文档一样精确，system prompt 给正确示例，输出解析层做容错——JSON 解析失败先用正则提取再重试一次。

### 第 6 题：分层记忆架构（1 分钟精简版）

两层设计。底层 Session Memory——所有原始消息存数据库，永不压缩，用于回溯和回查。上层 Compact Summary——早期对话压缩成结构化摘要注入上下文。

触发条件双阈值：Token 超模型最大上下文的 70%，或轮次超 10 轮且没触发过压缩。压缩时保留最近 4-6 轮不压。压缩用 qwen-turbo（成本低、速度快、中文摘要稳定），目标 200-300 token，组织成四段：核心问题、关键事实、偏好约束、未解决问题。上下文重组顺序：[系统提示] + [历史摘要] + [最近 N 轮] + [当前输入]。Hook 动态注入——用户切话题时不注入摘要，回归原话题时向量匹配重新载入。

防信息丢失四层：prompt 强制保留否定词和数字、后处理正则校验丢失就补入、用户可标记重要消息永不压缩、Memory Search Tool 从原始库回查。摘要 prompt 迭代了三版——第一版丢否定词，第二版丢数字，第三版太长。最终版强制要求保留否定词和数字、总长 ≤300 token。

**追问 6.1：为什么不直接用 128K 模型塞全部历史？**

三个原因。成本：每轮塞全部历史，10 轮轻松上万 token，乘以日活成本可观。延迟：长上下文推理慢。注意力稀释：模型对长文本中部关注度下降，塞得多不等于记得清。分层记忆是用工程手段解决「长上下文 ≠ 长记忆」。

### 第 7 题：MCP 协议（★ 从零构建）

MCP 解决的是 AI 应用对接外部工具的标准化问题。在 MCP 出现之前，这是 N×M 问题——每个 AI 框架要对接每个工具都要各写一套适配代码。MCP 定义了一套 Client-Server 标准通信协议，任何实现 MCP Server 的工具可以被任何 MCP Client 直接调用，把 N×M 变成 N+M。类比 USB 协议——设备实现了 USB 接口，任何电脑都能即插即用。

和 Function Calling 的核心区别是它们在不同层次。Function Calling 定义"LLM 怎么表达调用工具的意图"——输出 JSON 含工具名和参数，但不管工具在哪、怎么发现、怎么连接。MCP 定义"工具怎么被发现、连接和管理"——Server 通过 tools/list 声明能力，Client 通过 tools/call 调用，基于 stdio 或 SSE 长连接。概括：Function Calling 是 LLM 的"手语"，MCP 是工具接入的"USB 协议"。两者配合使用——MCP 负责发现和连接，Function Calling 负责表达意图，MCP 负责把请求发给 Server 并取回结果。

选型判断三标准：复用范围、部署方式、管理复杂度。需要多个 Agent 复用的工具做 MCP Server；逻辑简单几行代码、无复用需求的写成 Agent Tool。KnowOcean 的知识库检索目前只被一个 Agent 用，所以先写成 Tool。如果未来要开放给其他系统，会封装成 MCP Server，暴露 kb_search 和 doc_query 两个 tool。

**追问 7.1：有没有实际开发过 MCP Server？**

坦率说，了解协议规范但没实际开发过。如果要做，首选是把 KnowOcean 的知识库检索封装成 MCP Server——定义 Server 类实现 initialize、tools/list、tools/call 三个核心 handler，传输层选 stdio 因为和现有 Python 服务集成最方便。

**追问 7.2：MCP 和 REST API 有什么不同？**

三个核心不同。MCP 是双向通信——Server 可主动推送资源变更通知，REST 是请求-响应模型。MCP 有自己的语义规范——tools/list 声明能力、tools/call 执行调用、resources/read 读取数据——这些是协议层约定的，不是每个 API 自定。MCP 基于长连接，REST 是无状态短连接。所以 MCP 更像持续运行的"工具服务"，REST 更像被动的"数据接口"。

### 第 8 题：分块策略（★ 增强版）

先坦白说，项目是独立开发，没跑大规模对比实验。但参数不是拍脑袋定的，基于三个约束推导。

第一，语义完整性。目标是每个 chunk 承载一个最小语义单元——一个观点、一个步骤、一个定义。经过对产品手册和技术文档的抽样，中文中等段落约 300-480 字对应 200-280 token，定 240 token 保证大部分段落不被从中间切断。

第二，上下文窗口利用。qwen-max 单次最多塞 8-10 个 chunk。chunk 太大（512 token），10 个就 5120 token，挤占系统提示词和对话历史空间，且有效信息被稀释。太小（80 token），10 个只能覆盖很小范围，检索覆盖度不够。240 是平衡点。

第三，引用精度。要求引文精确到段落而不是章节，小 chunk 天然优势——检索出的 chunk 就是那个段落，不需要二次定位。

overlap=32 的逻辑：32 token ≈ 中文 48-64 字 ≈ 2-3 句话，能覆盖绝大多数"关键句落在 chunk 边界"的情况。测试过一个极端例子：两步操作说明恰好在 chunk 边界切断，32 token 的 overlapping window 把它完整兜回来。

如果要做正式实验：准备 50 条查询覆盖精确/模糊/跨段落三类，对比三组参数 240/32、512/64、120/16，评估 MRR、NDCG@5、答案引文上下文完整性（人工评分）。这是我的方法论——不是社区推荐就抄过来，而是基于场景约束做推导，有条件时用实验验证。

API 手册 vs 政策白皮书，策略绝对不同。API 手册每个方法是独立信息单元，用小 chunk 120-180 token 严格按方法边界切，metadata 保留方法签名。政策白皮书有逻辑链条前后文关联，用中 chunk 350-500 token 按段落/小节边界切，宁可稍大不断逻辑。理想做法是在 ETL 前加文档分类器自动选策略。

**追问 8.1：文档分类器怎么实现？**

先用规则层——根据文件扩展名和内容特征快速判断（代码密度高→technical，段落长连词多→narrative），能搞定 80%。剩下不确定的用一次轻量级 LLM 分类判断类型，结果缓存，同类型后续直接用规则。

**追问 8.2：metadata 怎么不丢失？**

每个 chunk 绑 source_doc_id + page_number + chunk_index + parent_section_title。PGVector 和 ES 各存一份 metadata，冗余成本可忽略，好处是无论从哪个通道出结果都能拿到完整引用信息。

### 第 9 题：技术分歧处理（★ 从零构建，STARR 模型）

在上家公司做电商时，关于订单列表页的缓存策略，我和组长有过一次分歧。我的方案是用 Redis 缓存订单列表全量数据，TTL 30 分钟——因为订单列表是访问量最高的接口，每次查 MySQL join 三张表响应 800ms 以上。组长认为订单状态会变（待支付→已支付→配送中），30 分钟缓存会让用户看到过期状态，经验上只缓存商品信息，订单部分实时查。

我怎么处理的？三步。第一步，不争对错先查数据。拉了线上订单状态变更的时间分布——90% 的订单从支付到发货超过 2 小时，30 分钟窗口内发生状态变更的不到 5%。数据过期风险比直觉小得多。

第二步，提折中方案。保留全量缓存但 TTL 从 30 分钟降到 5 分钟，同时在支付回调和发货回调通过 MQ 发缓存失效消息——主动失效 + 被动过期双重保障，过期风险从 5% 降到 1% 以下。

第三步，评审会用数据说话。三种方案对比：纯实时 800ms、我原方案 80ms 但有 5% 过期风险、折中方案 80ms 风险 <1%。数据一摆，团队很快通过折中方案。

上线后订单列表接口响应时间降低 65%，没出现过一例缓存不一致线上问题。一个月后组长复盘时说"你这个折中方案比我最初想的更全面"。

这次经历让我沉淀了两个原则。第一，技术分歧本质不是谁对谁错，而是不同 trade-off 的偏好——我偏性能，组长偏一致性，折中后都有。第二，工程决策最有说服力的不是谁资历深，而是谁带了数据。之后我养成了习惯——讨论方案前先把数据查了。

### 压力题 1：Java vs Python 的选型逻辑

两个技术栈我用在不同场景。Spring Boot + Java 优势是生态成熟、类型安全、适合大规模企业项目——电商的分布式事务 Seata、服务治理 Nacos/Sentinel 这些问题 Java 生态方案更成熟。FastAPI + Python 优势是开发效率高、异步原生支持好、AI 生态无缝衔接——LangChain、DashScope SDK、pgvector 客户端都是 Python 原生，省掉跨语言桥接。

选型原则很实际：以 CRUD + 事务 + 微服务治理为主的项目选 Spring Boot，以 LLM 调用 + 数据处理 + 快速迭代为主的 AI 应用选 FastAPI。两者不是竞争关系，是不同场景的工具。如果 KnowOcean 未来需要高并发用户体系和复杂权限管理，会考虑 Spring Boot 做用户和权限模块，FastAPI 做 AI 引擎，内部 API 或 MQ 通信。

---

### 压力题 2：40% 召回率提升的 baseline

这个数字的 baseline 是单路 PGVector 语义检索。50 条典型查询，纯向量检索 Top-5 召回率作为 baseline，加上 ES 关键词 + RRF 融合后提升 40% 以上。需要坦承的是，这个提升幅度大有一部分原因是 pure PGVector 本身在我的数据集上短查询关键词稀疏时召回率确实不高，混合检索的增益就显著。如果用更精细的向量调优（HNSW 参数、换 embedding 模型），单路 baseline 可能更高，提升幅度不会这么大。但不管怎么说，混合检索带来的提升方向是对的。

---

### 压力题 3：1000 个企业多租户方案

数据隔离：PGVector 不支持原生多租户，在每个 chunk metadata 中加 tenant_id 字段，检索时 WHERE 条件过滤。ES 同理，index mapping 加 tenant_id，查询时 filter context。不建独立 index——PGVector 和 ES 索引数量有上限，上千租户各自建不可维护。

计算资源分级：轻量级租户共享 PGVector 和 ES 集群，靠 tenant_id 隔离，成本低但存在 noisy neighbor 问题。重量级租户（文档量百万级）分配独立 PGVector schema 和 ES index，甚至独立模型推理实例。API 层面统一 Gateway 做租户身份验证，tenant_id 从 API Key 或 JWT 提取，透传到下游。Agent 对话记忆按 tenant_id + conversation_id 隔离。

---

### 压力题 4：LLM 调用成本

典型 Agent 模式问答：Query Planning 一次 LLM 调用，触发 HyDE 再加一次，最终答案生成一次。最小路径 2 次，最多 3-4 次。每次 input 约 2000-4000 token（检索 Top-5 chunk + 对话历史 + 系统提示），output 300-800 token。按 DashScope qwen-max 价格粗略算，单次几分到一毛多人民币。

优化空间：高频问题缓存检索结果和答案、简单问题降级用 qwen-turbo、检索结果 evidence_level 够 SUFFICIENT 就跳过 HyDE 直接生成、文档未更新时 embedding 缓存复用。

### 压力题 5：从零重做 KnowOcean

三个最重要改变。第一，一开始就引入 RAGAS 评估——建评估数据集和自动评估 pipeline，每次改参数或 prompt 都能立刻看指标变化。这是最大遗憾。

第二，Agent tool 接口按 MCP 协议设计——现在 tool 是项目内部自定义格式，如果一开始用 MCP 规范，后续接入外部工具和代码可移植性更好。

第三，更早分离关注点——现在检索、Agent 推理、对话管理在一个服务里。重来会拆成三个独立服务，内部 API 或 MQ 通信，各自独立迭代独立扩缩容。

---

### 压力题 6：RAG 评估方法

目前主要是人工评估——准备几十组「问题-期望答案」测试对，改代码改 prompt 后手动跑看效果。效率低、覆盖面窄、无法量化。

如果要产品化，引入 RAGAS 框架四维自动化评估：Faithfulness（答案是否基于检索文档）、Answer Relevancy（是否切题）、Context Precision（相关文档排名）、Context Recall（是否找全）。建 Golden Dataset——人工标注 100-200 条查询的正确文档和期望答案作为 ground truth。每次改动后 RAGAS 自动跑四个指标，同时保留人工抽检因为自动化评估和人工感受偶尔有偏差。

---

### 压力题 7：对 LangChain 的批评怎么看

业界的批评有道理——抽象层次太多、debug 困难、版本不稳定。我踩过坑：链式调用出错时，报错层层包装根本看不出哪层哪个参数传错了，只能看源码定位。

但我还是用 LangChain，因为它在项目初期省了大量时间。ConversationBufferMemory、RetrievalQA、AgentExecutor 这些组件如果从零实现要很久，用 LangChain 几行配置搞定。我的策略是「渐进式脱离」——初期用 LangChain 快速跑通 MVP，后续对性能和稳定性敏感的模块逐步替换成自己实现。比如 KnowOcean 的混合检索就是自己写的，没用 LangChain 的 retriever 抽象，因为要精确控制 ES 和 PGVector 并发查询和 RRF 融合细节。LangChain 是梯子不是拐杖——用它加速启动，但不依赖它一辈子。
