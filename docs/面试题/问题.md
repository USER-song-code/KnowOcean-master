### 当用户问了一个短问题，比如只有两三个词（像"退货政策"），PgVector 语义检索可能召回的是关于配送而不是退货的文档，Elasticsearch 关键词匹配也可能因为太短而发散。你们在实际项目中遇到过这种情况吗？具体怎么处理的？
实际场景中我们确实遇到过，短查询对语义检索和关键词匹配都不太友好，所以设计了分层处理，一共四层：

第一层：预处理层（查询规划）

Query Rewrite：将短查询补充为更完整的规范表达，例如“退货政策” → “商品的退货政策是什么？”

Multi-Query Expansion：基于原始短查询生成同义词或相关变体，并发检索后融合结果。

Query Decomposition：如果用户问的是“退货政策和配送时间”这种复合短查询，会拆成两个子查询分别处理；纯短查询如“退货政策”则不触发分解。

第二层：短查询召回策略

当检测到查询长度 ≤ 3 个词且没有明显实体信息时：

提高 ES 的 match_phrase 权重，要求词项连续或接近。

对 PgVector 使用较低的相似度阈值。

引入 HyDE（假设文档）：先让 LLM 基于短查询生成一段伪文档，再用伪文档做向量检索。

这里补充一个 trade-off：HyDE 确实会增加一次 LLM 调用，带来额外的延迟（大约 0.5~1 秒）。我们的权衡是：

仅对短查询且首次检索结果相关性低于阈值的情况触发 HyDE，不是所有短查询都走 HyDE。

同时配合 意图映射表（第三层）和高频缓存，大部分常见短查询可以直接命中，绕过 HyDE。

实际线上统计中，大约 30% 的短查询会触发 HyDE，这部分用户的体验提升（从无相关结果到有相关结果）远大于增加的延迟，而且我们通过流式返回 + 前端加载提示，让用户感知不到明显等待。

第三层：业务规则层

内置高频短词 → 标准查询的映射表，例如“退货政策”直接定向检索标签为 policy_return 的文档，“免邮”映射到 shipping_free。支持运营配置和历史日志自动挖掘。

第四层：兜底与反馈

如果以上步骤后召回结果相关性仍然低于阈值，则返回一个澄清性问题，例如“您想了解退货的期限、运费还是流程？”

同时记录这条失败的 query，用于后续微调 Embedding 或扩充同义词库。

### 你在 KnowOcean 中用了 ReAct 模式做 Agent。请用你自己的话解释一下：ReAct Agent 的 Thought → Action → Observation 循环是怎么运作的？和普通的 Chain（比如 Sequential Chain）相比，核心区别是什么？什么时候该用 Agent 而不是 Chain？
我们设计了三个层次的终止机制：

最大步数限制：每个 Agent 会话最多执行 5 轮 Thought-Action-Observation 循环。超过后强制输出当前最佳答案（或提示“问题太复杂，请简化”）。5 轮是根据线上统计选出的阈值——绝大多数问答在 2-3 轮内就能解决。

Token 预算控制：每轮消耗的 token（包括 Thought 输出、Action 参数、Observation 内容）累计超过 4000 时会中断，避免成本失控。这个预算会随用户等级或场景动态调整（比如内部员工可以更高）。

LLM 自主判断 + 置信度阈值：每轮 Observation 后，LLM 除了判断“够不够”，还会输出一个 0-100 的置信度。如果连续两轮置信度没有提升（比如 45→47→46），或者置信度低于 30%，则提前终止并转向澄清式回复。

另外还有一个隐性终止：当 Agent 调用的工具返回明确错误（比如知识库无结果、API 超时）且没有备用工具时，直接输出兜底话术，不再继续循环。

在 KnowOcean 里，我们把这些终止信息也通过 SSE 推送前端，用户会看到“已达到最大分析步数，为您总结当前信息”或“问题不够明确，请补充细节”。

### 你在简历中提到 KnowOcean 设计了 Session Memory + Compact Summary 分层记忆架构，能稳定支持 10+ 轮对话。请说说这个分层记忆体系的具体设计：什么条件下触发摘要压缩？压缩后的摘要怎么和新的对话上下文合并？有没有遇到过摘要压缩后丢失关键信息的情况？

好的，面试官，我来完整回答一下这个关于分层记忆架构的问题。

我们在 KnowOcean 中设计了 Session Memory + Compact Summary 的两层记忆体系：

Session Memory：存储原始会话消息，保存到数据库中，永不压缩。主要用于追溯、回查、以及支持后续的 Memory Search Tool 检索。

Compact Summary：摘要压缩层。当对话超过一定阈值后，将早期对话压缩成结构化摘要，替换掉较旧的原始消息，作为后续对话的长期记忆注入上下文。

一、触发摘要压缩的条件
我们采用了 双重阈值 + 主动压缩 策略：

Token 阈值：系统会检测当前对话上下文（系统提示词 + 历史消息 + 当前用户问题）的总 token 数，当超过模型最大上下文（如 128K）的 70% 时触发压缩。预留 30% 空间给即将生成的新回复和后续轮次。

轮次阈值：当原始消息轮次超过 10 轮，且摘要压缩未被触发时，主动触发一次压缩。

手动/预压缩：用户长时间无操作后重新发起对话，或系统检测到 token 溢出风险时，在后台异步进行一次预压缩，避免实时压缩带来延迟。

二、压缩后的摘要如何与新的对话上下文合并
具体流程：

保留近期原始消息：我们保留最近 4-6 轮原始消息（约 2-3 组问答）不压缩。因为近期的对话通常包含尚未落地的意图或待确认信息。

生成摘要：调用一个轻量级模型来处理。我们使用的是 DashScope 的 qwen-turbo，原因是成本低、速度足够、能力匹配。

摘要生成有专门的 prompt（后面细说）。

摘要的目标长度控制在 200-300 token 之间，实验得出这个区间信息保留和压缩效果最好。

上下文重组：新的对话上下文按照以下顺序拼接：
[系统提示] + [历史摘要] + [最近 N 轮原始消息] + [当前用户输入]

其中“历史摘要”如果经过多次压缩，会递归合并：第一次压缩产生摘要1，第二次压缩时把摘要1 + 新一批消息再次生成摘要2（摘要的摘要）。

注入策略（Hook 动态机制）：根据当前用户问题与历史摘要的语义相关性，决定是否加载摘要。如果用户突然切换话题（与摘要内容明显无关），摘要暂时不注入，只使用近期窗口；等对话回归原话题时，再通过向量相似度匹配重新载入摘要。

三、摘要模型的细节与调优
模型选择：qwen-turbo。我们在测试中对比过其他轻量模型（比如 baichuan-turbo），qwen-turbo 在中文摘要任务上更稳定，且延迟稳定在 0.5-1 秒内，适合后台异步调用。

摘要 prompt 的迭代：
我们经过多轮调优，最终版本大致如下（口语描述）：

你是一个对话摘要助手，请将以下对话历史压缩成结构化摘要，保留：1）用户的核心问题；2）关键事实（数字、价格、时间、实体名称）；3）偏好或否定表达（例如“不喜欢”、“不要”）；4）未解决的问题。输出格式为：用户核心问题：…；关键事实：…；偏好/约束：…；未解决问题：…。摘要总长度不超过 300 token，不要添加解释，必须保留原文中的否定词和数字。

调优过程中遇到的问题：

第一版没有强调保留否定词，结果丢失了“不喜欢红色”这类关键信息 → 增加了“必须保留否定词”。

第二版摘要常常把“99元”概括成“有价格” → 强制要求数字原文保留。

第三版摘要过长（超过 500 token），压缩效果不明显 → 增加了 300 token 长度限制，并加入简单的截断策略：优先保留“关键事实”和“偏好/约束”段落。

长度控制：摘要生成后我们会做 token 计数，超过 300 则进行字段级截断（关键事实 > 偏好/约束 > 核心问题 > 未解决问题），保证最长不超过 350 token。

四、遇到信息丢失及解决方案
遇到过，而且不止一次。 典型案例：

用户说“我不喜欢红色”，摘要被压缩成“用户对颜色有偏好”，丢失了“不喜欢”。

用户说“价格是 99 元，但我要用积分抵扣”，摘要只保留了“价格 99 元”，丢了积分抵扣信息。

解决方案：

压缩时强制保留信号词：通过 prompt 要求模型保留否定词、数字、关键实体，并在后处理中用正则提取否定词和数字，如果发现丢失就强制补入摘要的“偏好/约束”段落。

重要标记机制：用户可以在前端对某条消息标记“重要”，系统在压缩时会跳过这些重要消息，永不压缩，始终以原始形态保留在上下文中。

可追溯的回查能力（Memory Search Tool）：即使摘要丢失了信息，当用户后续追问（例如“我之前说过不喜欢什么颜色？”）时，Agent 会调用一个工具，在原始的 Session Memory 数据库中进行向量检索或关键词检索，找到相关原始消息片段，重新注入当前上下文。这相当于把摘要当作快速索引，原始消息当作完整归档。

定期评估 + 人工校准：我们在测试集上定期跑评估，检测摘要是否遗漏关键信息。如果发现某类信息（比如否定、时间边界、数字）经常丢失，就调整摘要 prompt 或增加后处理规则，不断迭代。

总结一下：我们通过 双重阈值触发压缩、滑动窗口保留近期消息、轻量级模型生成结构化摘要，并且配合 Hook 动态注入 来支持 10+ 轮对话。对于信息丢失，通过 强制保留信号词、重要标记跳过、可回查原始记忆 以及 定期评估 来兜底。这就是完整的 Session Memory + Compact Summary 分层记忆架构。

### Spring Cloud 微服务具体用了哪些组件？Nacos、Sentinel、Gateway、Seata 怎么配合的？

蔬蔬买菜项目用的是 Spring Cloud Alibaba 全家桶，核心四个组件。

### MySQL 索引优化，能举一个具体案例吗？

**回答方式**：用一个真实的慢 SQL 案例——讲场景、explain 看到了什么、加了什么索引、效果差多少。

蔬蔬买菜订单列表页有一个典型慢查询。场景是运营后台查订单列表，SQL 大致是 `SELECT * FROM orders WHERE user_id = ? AND status = ? AND create_time BETWEEN ? AND ? ORDER BY create_time DESC LIMIT 20`。

explain 发现 type 是 ALL，全表扫了 30 万行。表上只有一个 user_id 的单列索引，status 和 create_time 都没走索引，ORDER BY create_time 触发了 filesort。

我建了一个联合索引 `(user_id, status, create_time)`。这个顺序是有讲究的——user_id 是等值查询放最左，status 也是等值查询放第二，create_time 有范围查询也有排序需求放最后，这样索引覆盖了 WHERE 的三列和 ORDER BY 的一列。

建完索引后 explain 显示 type 变 ref，key_len 显示用了全部三列，Extra 里 filesort 消失了。实际查询时间从 2.3 秒降到 50ms 左右。

### Redis 持久化，RDB 和 AOF 你们怎么选的？有没有遇到过数据丢失？

**回答方式**：两种方案各自一句话概括特点，再说实际选型和理由，最后承认遇到过丢数据并讲如何修复预防。

RDB 是定期快照——优点是恢复快、对性能影响小，缺点是两次快照之间的数据可能丢。AOF 是追加日志——优点是更安全，缺点是文件大、恢复慢。

蔬蔬买菜用的是混合持久化（Redis 4.0+）：RDB 做全量快照 + AOF 记录快照期间的增量，持久化频率设的是 AOF 每秒 fsync 一次——不丢超过 1 秒的数据，对性能影响可控。

数据丢失确实遇到过一次。服务器异常断电，AOF 文件尾部损坏，Redis 重启失败。最后用 redis-check-aof 工具修复去掉了不完整的尾部命令，重启恢复。之后加了两件事：定时任务每天备份 AOF 到另一台机器，代码层加了缓存穿透保护——Redis 不可用时走数据库兜底。

### Docker + Serverless 平台怎么用的？冷启动延迟怎么处理？

**回答方式**：先说什么 Serverless 平台，再说冷启动处理，最后说 FastAPI 在 Serverless 上跟传统部署有什么不同。

用的是阿里云函数计算（FC）——把 FastAPI 项目打成 Docker 镜像推到容器镜像仓库，FC 按请求量自动扩缩容实例。Dockerfile 是 Python 多阶段构建：第一阶段装依赖，第二阶段只保留运行时最小体积。

冷启动延迟是 Serverless 的痛点——容器首次启动 2-5 秒。处理方式：镜像体积压到最小（python:3.11-slim），启动阶段只加载必需依赖；设最小保留实例 1 个，保证至少一个热启动；DashScope SDK 延迟加载，不进启动主路径。

FastAPI 在 Serverless 上跟传统部署三个不同：一是服务必须无状态，所有状态放 Redis 或数据库（Serverless 实例随时回收）；二是 SSE 流式请求的超时单独配到 120 秒（默认 60 秒不够长对话）；三是连接池大小控制在 5 以内（每个实例独立，避免撑爆数据库连接数）。

### 「多 Agent 协作」具体指什么？多个 Agent 之间怎么通信和协调？

**回答方式**：先诚实说明 KnowOcean 目前是单 Agent，然后讲对多 Agent 协作的理解和场景判断。面试官要的是思考深度，不是编造经验。

### 为什么选 PgVector 而不是 Milvus、Weaviate 或 Pinecone？HNSW 索引参数怎么调的？

**回答方式**：四选一对比各有优劣，说清选型逻辑和边界条件。

选 PGVector 核心原因是场景匹配——KnowOcean 十万级向量、单机部署、团队小。

Milvus 性能最强能撑十亿级向量，但需要独立部署运维，对当前规模太重。Weaviate 功能全但模型绑定紧，自带向量化不够灵活。Pinecone 全托管最省心但数据不在自己服务器上，按请求量计费成本随调用量涨——长期不如自己维护 PGVector 划算。

PGVector 刚好满足三个需求：与业务数据同一 PostgreSQL，一个库搞定所有存储；会用 PostgreSQL 就会 PGVector，运维门槛为零；十万级向量 HNSW 索引查询稳定 20-50ms。

HNSW 索引参数设 m=16, ef_construction=200。m 控制每层节点连接数——16 跟 1024 维向量匹配，连接太多构建慢、太少精度降。ef_construction 控制构建时搜索宽度——200 是精度和构建时间的平衡点。

边界条件：上了千万级向量、纯向量检索成为瓶颈时换 Milvus 做纯向量检索层，PGVector 回归业务数据存储。

### 「支持最多 3 路查询并发检索」，哪三路？

### RRF 融合排序跟简单的加权求和相比，RRF 好在哪？

加权求和的痛点：两通道分数量纲完全不同——PGVector 余弦相似度是 [-1,1] 之间的小数，ES BM25 可以根据文档长度和词频涨到几十上百。加权求和必须人工设权重比例（w1 给 PGVector、w2 给 ES），这个比例极其敏感且依赖数据集。

RRF 不碰原始分数，只看排名。公式 score = Σ 1/(k + rank)。不管你 PGVector 第一名分数是 0.95 还是 ES 第一名是 45，在 RRF 里只看你是第几名。从根本上回避了量纲对齐问题。

Learning to Rank 想过但没做——需要大量标注训练数据，独立开发成本太高。将来数据够的话会考虑用 xgboost 学习更复杂的融合特征。

### RAG 系统怎么评估好坏？用过 RAGAS 吗？

目前主要是人工评估——准备几十组"问题→期望答案"测试对，改参数后手动跑看效果。

如果要系统化评估，分两层。检索层看 MRR（第一个相关文档的排名）和 NDCG@5（Top 5 整体排序质量）。生成层看四个 RAGAS 指标：Faithfulness（答案基于检索文档还是模型自己编的）、Answer Relevancy（是否切题）、Context Precision（相关文档排名）、Context Recall（是否找全）。

做法是建 Golden Dataset——人工标注 100-200 条查询的正确文档和期望答案作为 ground truth，每次改动 RAGAS 自动跑四个指标，同时保留人工抽检（自动化评估和人工感受偶尔有偏差）。坦白说这是目前的一个短板——如果重做会在所有功能开发之前先把评估框架搭好。

### SSE 连接断了怎么办？Agent 推理到一半出错怎么处理？

SSE 连接断开：前端用 EventSource 的自动重连机制——浏览器原生支持断开后自动重试，间隔递增。同时维护"消息 ID"——重连后带 `Last-Event-ID` header，后端定位断点继续推送。断开超 10 秒且重连失败，前端显示"连接已断开，请刷新重试"并保留已收到的部分。

Agent 推理出错：工具调用失败（无结果、超时）→ 有备用走备用，没备用输出兜底话术。LLM 返回格式不可解析 → 正则提取重试一次，两次失败直接结束本轮。SSE 推送中途异常 → try-catch 捕获后发 `{"event": "error", "data": "处理中断"}` 给前端，前端保留已展示内容并提示。

### 下单扣库存的分布式事务怎么处理的？

下单涉及三个微服务——订单（创建）、库存（扣减）、账户（扣余额）。三个操作要么全成功要么全回滚。

用 Seata AT 模式。原理是两阶段：一阶段各服务执行 SQL，Seata 自动生成 undo log；二阶段全部成功则提交（删 undo log），任一失败则回滚（用 undo log 反向补偿）。

实际流程：Gateway 接请求 → 订单服务 @GlobalTransactional 开启全局事务 → Feign 调库存扣减 → Feign 调账户扣余额 → 全部成功 Seata TC 全局提交。库存失败返回异常则 TC 全局回滚——订单删掉已创建的记录，库存恢复已扣数量。

### 为什么用 Shiro 而不是 Spring Security？

团队对 Shiro 更熟悉——之前项目一直用，迁移成本低。Shiro 更轻——配 RBAC 几行代码搞定，不需要 OAuth2/LDAP 这种复杂认证。RBAC 表结构是五张表：user、role、permission、user_role、role_permission。三级权限：角色级（进菜单）、菜单级（看页面）、接口级（调 API）。Controller 方法加 @RequiresPermissions 注解配合 AOP 自动校验，权限数据存 MySQL，用户登录时加载一次后缓存 Redis，Token 有效期 2 小时。

### 抽奖活动高并发下怎么防超卖？

核心方案是 Redis 奖品库存计数 + Redisson 分布式锁扣减互斥。流程：用户点抽奖 → Redis 查剩余库存 → 大于 0 才进入抽奖逻辑 → Redisson 分布式锁锁住该奖品 → 锁内双重检查库存 → 扣库存 → 释放锁 → 抽奖结果入异步队列写库。

不用数据库行锁因为高并发下等待和超时严重，Redis 原子操作性能高几个数量级。锁内双重检查是最后防线——99.9% 的情况 Redis decr 本身就能挡住，0.1% 是兜底。红包金额防超发类似——总预算在 Redis 实时递减，剩 5% 停止并发直接转先到先得。

### 为什么用 MongoDB 的地理索引而不是 MySQL 空间索引或 Redis GEO？

MySQL 8.0 空间索引支持 R 树理论可行，但当时用 5.7 支持不完善，且配送区域数据是 GeoJSON 格式——MongoDB 对这种格式原生支持更好，存进去直接建 2dsphere 索引查询。

Redis GEO 底层是 ZSET + Geohash，做"附近 XX 公里"圆形查询非常快。但蔬蔬买菜是不规则配送区域（商家覆盖几个小区但不到另一个），不是简单半径——GEO 做不了多边形覆盖判断。MongoDB 的 2dsphere + GeoJsonPolygon 原生支持这个。

所以 MongoDB 刚好卡在两个方案都覆盖不到的位置——既要不规则多边形地理查询，又要文档型数据库灵活性存配送区域复杂结构。

### POI 大数据量 Excel 导出会不会 OOM？

确实遇到过 OOM 风险——运营导出半年订单明细几十万行，普通 XSSFWorkbook 整个工作簿加载内存直接撑爆。

解决方案三管齐下。导出改异步——前端点导出立刻返回"任务已创建"，后台生成完通知下载，避免 HTTP 超时。数据库分页查询——每次只取 1000 条用游标（ResultSet.TYPE_FORWARD_ONLY）保证结果集不一次性进内存。Excel 用 SXSSFWorkbook 流式写入——只在内存保留最近 100 行窗口，其余刷临时磁盘文件。10 万行约 10-20 秒导出，内存稳定 200MB 以内。
