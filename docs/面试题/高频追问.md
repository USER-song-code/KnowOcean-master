## 一、RAG 检索链路

### 第 1 题：为什么这样设计 workflow？

**回答方式**

按「问题 → 设计 → 不做会怎样」的结构，把 workflow 每一步讲清楚。每步一句话说明：这一步解决什么问题、怎么解决的、跳过去会出什么事。最后收一句总结——这个 workflow 是踩坑踩出来的，不是画出来的。

**回答**

KnowOcean 的 RAG workflow 分五个阶段，每个阶段解决一个具体问题。

第一阶段：文档 ETL。问题是原始文档有四种格式、非结构化、无法直接参与检索。所以设计了统一流水线——解析 → 清洗 → 结构感知切块（240 token）→ 向量化。不做这一步，后面的检索根本没数据可查。

第二阶段：双通道入库。问题是单一向量检索对短查询、专业术语匹配不好，单一关键词检索又理解不了语义。所以一个 chunk 同时写 PGVector（HNSW 索引做语义检索）和 ES（IK 分词做关键词检索），走 asyncio.gather 并行。这样语义查得到相似内容，关键词也匹配得到精确术语。

第三阶段：Query Planning。问题是用户提问不规范——口语化、含多个子问题、表达模糊。所以加了 LLM 驱动的查询规划：Query Rewrite 把口语转规范表达，Query Decomposition 拆复合问题，Multi-Query Expansion 生成同义变体。不做这一步，原始口语送到检索器命中率很低。

第四阶段：混合检索 + RRF 融合。问题是两通道返回的结果怎么合并？各自排名尺度不同，不能直接加。所以用 RRF 做融合排序，再 cluster 聚合去重、邻居窗口扩展补全上下文。不做融合，两条结果列表割裂，用户得不到完整答案。

第五阶段：证据评估 + 生成。问题是检索结果质量参差不齐，差的结果直接给 LLM 会产生幻觉。所以加了 4 级证据评估——NONE/WEAK/PARTIAL/SUFFICIENT——不够就降级回答甚至拒答。最终通过 SSE 流式返回带引文的答案。

总结：这个 workflow 每一步都是在堵具体的坑，不是预先设计的精美架构，而是边踩坑边迭代出来的。

### 第 2 题：Chunk 怎么切？

**回答方式**

先说参数（240/32）的推导逻辑，用到哪三个约束。再说不同文档用不同策略。最后坦诚说没做大规模 A/B 实验，但要补上"如果做实验会怎么做"的方法论，让面试官看到你知道怎么做只是资源不够。

**回答**

我用 target-tokens=240, overlap=32。坦白说没跑大规模对比实验，但参数基于三个约束推导的。

约束一，语义完整性。目标是每个 chunk 承载一个完整的最小语义单元——一个观点、一个步骤、一个定义。分析典型技术文档后，中文一个中等段落约 300-480 字对应 200-280 token，所以定 240。

约束二，上下文窗口利用。qwen-max 单次最多塞 8-10 个 chunk。太大（512）10 个就 5120 token 挤占系统提示词空间且有效信息稀释，太小（80）覆盖范围不够。240 是平衡点。

约束三，引用精度。要求引文精确到段落，小 chunk 天然优势——检索出来的直接就是那个段落。

overlap=32 的逻辑：约 2-3 句话的重叠，覆盖"关键句落在 chunk 边界"的情况。实测过一个极端例子——两步操作说明在边界切断，32 token overlapping 完整兜回来了。

不同文档绝对不用同一套策略。API 参考手册用小 chunk 120-180 token 严格按方法边界切，政策白皮书用中 chunk 350-500 token 按段落边界切，对话/QA 按问答对切。理想做法是 ETL 前加文档分类器——规则判断 80%，剩下的用一次轻量级 LLM 判断。

如果做正式实验：准备 50 条查询覆盖精确/模糊/跨段落三类，对比三组参数（240/32、512/64、120/16），评估 MRR、NDCG@5、答案引文上下文完整性（人工评分）。

### 第 3 题：召回怎么做？

**回答方式**

先回答"为什么要双路"——单路的短板是什么。再说具体实现——用的什么工具、怎么并发、怎么融合。最后收一句选型原则。

**回答**

我用的是 PGVector 语义检索 + Elasticsearch 关键词检索的双路召回。

为什么需要双路？单向量检索对短查询、专业术语效果不好——搜"API 限流"，PGVector 可能召回相似的"流量控制"但漏了精确的"rate limiting"。单关键词检索理解不了语义——搜"怎么加快速度"，ES 匹配字面词，不会关联到"性能优化"。两路互补。

具体实现：PGVector 用余弦相似度在 HNSW 索引取 Top 50，ES 用 BM25 算法取 Top 50，asyncio.gather 并行发请求，检索层延迟控制在 50ms 内。

融合用 RRF，k=0——更信任两通道都排前面的结果，在测试集上精度比 k=60 高约 8%。融合后 cluster 去重 + 邻居窗口扩展补全上下文，最后过一个 4 级证据评估，低分的直接降级或拒答。

**追问：你们为什么用 ES 做关键词检索？用 PostgreSQL 的 tsvector 不够吗？**

**回答方式**

从场景需求讲起——为什么需要关键词检索、对比了哪些方案、为什么 ES 胜出。坦诚说 PG 的 tsvector 能用但不好用，ES 在中文分词和运维成熟度上更优。

**回答**

选 ES 的原因要从场景说起。我们的知识库里有很多技术文档，用户经常搜索精确的术语——"API 限流"、"RBAC 权限"、"HNSW 索引"。这些问题只靠向量检索是不够的，因为向量检索是语义相似，不是精确匹配。搜"API 限流"可能召回"流量控制"，但漏掉用户想要的那个页面。所以我们需要一路关键词检索来兜底精确匹配。

对比过几个方案。第一个是 PostgreSQL 自带的 tsvector 全文检索。能用，但中文分词很弱——PG 的中文分词要靠 zhparser 或 jieba 扩展，分词效果远远不如 ES 的 IK 分词。而且 tsvector 的 BM25 评分是简易版的，相关性排序不如 ES 成熟。

第二个是 MySQL 的全文索引。更不行，MySQL 的全文索引在中文场景基本不可用。

第三个就是 Elasticsearch。IK 分词插件对中文分词质量很好——"API限流策略"能正确分成"API/限流/策略"三个词。BM25 算法的相关性打分在中文文档搜索场景下效果有保障。而且 ES 的聚合能力还可以顺带做热词统计、文档分类这些附加功能。

还有一个工程上的考虑：当时团队没有其他人有 ES 运维经验，但 ES 的生态成熟度意味着网上能查到大多数问题的解决方案。PG tsvector 出了问题可能查半天找不到答案。选技术方案不只是选功能，也是选社区和生态。

当然，加 ES 也引入了运维复杂度——多维护一个集群、数据同步延时、磁盘占用翻倍。权衡下来，搜索质量提升远大于运维成本，所以选了 ES。

### 第 4 题：rerank 干什么的？

**回答方式**

先说粗排和精排的分工——检索要有速度和覆盖面，rerank 要有精度。再说 KnowOcean 里 rerank 的实际体现（RRF 融合 + 证据评估）。最后提一句如果要做更精细的 rerank 会怎么选模型。

**回答**

rerank（重排序）是在粗排检索之后的一个精排步骤。

检索追求速度——PGVector HNSW 和 ES BM25 都是近似算法，在百万级向量里快速找 Top 50 候选，但排序精度是牺牲了的。rerank 追求精度——对这 50 个候选做深度语义匹配，给每个文档打精确的相关性分数重新排一遍。

在 KnowOcean 里，rerank 的实际体现是两层。第一层是 RRF 融合——两个通道各自 Top 50 合并后，RRF 本质上就是一个跨通道的 rerank。第二层是证据评估——4 级评分（NONE/WEAK/PARTIAL/SUFFICIENT  无/弱/部分/足够）对每个 chunk 做精细打分，低分不进生成阶段。这两个机制加起来，就是 rerank 在我这个场景下的工程落地。

如果要做更精细的 rerank，会引入专门的重排序模型如 bge-reranker-large 或 Cohere Rerank，对 Top 50 做 cross-encoder 级别的深度匹配。但目前 KnowOcean 靠 RRF + 证据评估已经能满足需求，复杂度没往上加。

## 二、模型与优化

### 第 5 题：Prompt 怎么优化？

**回答方式**

用 KnowOcean 里摘要 prompt 的真实迭代做案例。第一版 → 出了什么问题 → 第二版怎么改 → 又出新问题 → 第三版最终方案。最后总结三条 prompt 优化经验。

**回答**

我讲一个真实案例——记忆压缩的摘要 prompt 优化，迭代了三版。

第一版：`将以下对话总结为简短摘要，保留关键信息。` 问题：把"我不喜欢红色"概括成了"用户对颜色有偏好"，丢了否定词。对系统来说这是致命的信息丢失——用户明确说不喜欢什么，后续推荐还推那个颜色，体验崩了。

第二版：加了`必须保留原文中的否定词和数字`。新问题：把"99 元但要用积分抵扣"压缩成"有价格"，丢了积分抵扣。而且有时候摘要超过 500 token，压缩不明显。

第三版（最终版）：定义结构化输出四个字段——用户核心问题、关键事实（强制数字原文）、偏好/约束（强制保留否定词）、未解决问题。加总长限制 300 token，超出按优先级截断：关键事实 > 偏好/约束 > 核心问题 > 未解决问题。后处理加正则校验——如果关键词在摘要里找不到，强制补入。

三条经验：一是 prompt 改完要在固定测试集上跑评估，不能凭感觉；二是 Few-shot 示例往往比规则指令更有效；三是 prompt 是概率输出，永远不可靠，关键信息用正则再兜一层。

### 第 6 题：embedding 怎么选？

**回答方式**

给结论 → 四维度展开说理由 → 对比候选方案 → 总结选型原则。

**回答**

我选的是阿里 DashScope 的 text-embedding-v3，考量了四个维度。

第一，语义质量。对比过 text-embedding-v2——v3 中文语义区分度明显更好。调研过 bge-large-zh，开源质量不错但需要自建推理服务，当时团队小运维成本划不来。

第二，维度与性能。1024 维信息密度够高，同时不会像 1536 维那样检索计算重。PGVector 建 HNSW 索引后，10 万级向量余弦相似度查询稳定在 20-50ms。

第三，生态一致性。LLM 也是 DashScope 的 qwen-max，embedding 用同一生态意味着统一的 API 管理、鉴权、费用结算——工程上省心。

第四，MTEB 中文榜单。text-embedding-v3 在中文语义相似度和分类任务上的 MTEB 得分在同类 API 产品里属于第一梯队。

总结选型原则：除非有明确证据证明另一个模型在核心指标上领先 10% 以上，否则生态一致性优先——同一套鉴权、同一张账单、同一条 SDK，运维成本比模型微小差异更重要。

## 三、Agent 架构

### 第 7 题：多 Agent 为什么比单 Agent 好？

**回答方式**

先澄清——不是所有场景都更好。然后给出多 Agent 的三种优势场景（任务可拆解、能力需隔离、质量需校验），每个场景带一个具体例子。最后坦诚说 KnowOcean 是单 Agent，因为场景不需要。面试官喜欢听判断标准，不喜欢听"多就是好"。

**回答**

先说实话——多 Agent 并不是在所有场景都比单 Agent 好。单 Agent 在任务简单、流程固定的时候反而更可靠、成本更低、调试更方便。

多 Agent 的优势体现在三个场景。

第一，任务天然可拆解。比如"调研三家竞品的功能差异，然后写一份对比报告"——可以拆成三个子 Agent 各自调研一家，再汇总给一个汇报 Agent 写报告。单 Agent 也能做，但在一个循环里反复调工具切上下文，效率低且容易走偏。

第二，能力边界需要隔离。不同 Agent 用不同的 system prompt 和工具集各自专注。比如一个 Agent 专门做检索，prompt 优化成"忠实、准确引用"；另一个专门做推理分析，prompt 优化成"批判性思考"。单 Agent 把所有指令塞一个 prompt，模型容易顾此失彼。

第三，质量需要互相校验。两个 Agent 独立推理后交叉验证——一个从文档 A 找数据，另一个从文档 B 找，两个结果互校。这比单 Agent 自问自答更可靠。

但多 Agent 代价也很大——成本成倍增加、延迟叠加、Agent 间通信可能引入新错误。KnowOcean 目前是单 Agent 架构，因为知识库问答场景够聚焦，单 Agent 配合 ReAct 推理 + 工具调用已经够用。多 Agent 在"分析-推理-校验"型任务上有优势，但"检索-问答"型任务用单 Agent 就够了。

## 四、存储与基础设施

### 第 8 题：Memory 怎么存？

**回答方式**

分层讲——Session Memory 存什么、表结构什么样；Compact Summary 存什么、字段怎么设计。最后说为什么用 PGVector 做记忆存储（一张表同时存原始消息和 embedding）。

**回答** 

KnowOcean 的记忆分两层存储。

第一层，Session Memory——原始对话消息。用 PostgreSQL 存，表结构：`session_id + conversation_id + role（user/assistant/system）+ content + metadata（token 数、是否标记重要、是否已压缩）+ created_at`。索引建在 `session_id + created_at` 上，支持按时间拉全部历史。

第二层，Compact Summary——压缩后的摘要。也存 PostgreSQL，字段：`session_id + summary_type + content（JSON，含四段：核心问题/关键事实/偏好约束/未解决问题）+ compressed_at`。上下文组装时直接从数据库拉 latest 摘要 JSON 拼到 prompt 里。

PGVector 存原始消息的 embedding 向量——这是为了 Memory Search Tool 检索。当用户追问"我之前说过不喜欢什么颜色？"，Agent 调 Memory Search Tool 用当前 query 做向量检索，在原始消息库里找最相似的几条重新注入上下文。为什么用 PGVector 而不是 MySQL 存原始消息？因为 PGVector 能同时存原始消息和 embedding 向量，检索和存储一个库搞定，架构更简单，而且向量检索和 SQL 过滤可以在一条查询里完成。

### 第 9 题：向量库原理？

**回答方式**

从"为什么传统索引不行"讲起，引出 HNSW 算法的大白话解释（多层图，上层粗定位下层精搜索），再落到 PGVector 的具体实现。最后对比 PGVector 和其他向量库的优劣，说清楚选型逻辑。

**回答**

向量数据库的核心任务是近似最近邻搜索——在百万级高维向量中快速找到与查询向量最相似的 Top K 个。

传统数据库用 B+ 树做索引，但 B+ 树对高维向量完全失效——高维空间的"距离"没有线性顺序可言。向量库用近似索引算法，牺牲一点精度换速度。

PGVector 用的是 HNSW 算法。可以这样理解：给向量建一个多层图。上层节点少、跳得远，做粗定位；下层节点密、跳得近，做精搜索。查询时从最上层开始，找离查询向量最近的节点，逐层往下，每层都在附近转几圈找到更近的，到最底层拿到最终 Top K。整个过程就像从卫星地图（上层）放大到街道地图（下层）找目的地。

PGVector 相比专用向量库的优势和劣势都很明显。优势一是与 PostgreSQL 深度集成——向量和业务数据在同一个库里，SQL 可以同时做向量检索和字段过滤（`WHERE tenant_id = ? ORDER BY embedding <=> query_vector`）。优势二是运维成本低——会用 PostgreSQL 就会用 PGVector。劣势是纯向量检索性能不如 Milvus——十亿级向量时 Milvus 的分布式索引比 PGVector 单机 HNSW 快一大截。

KnowOcean 目前十万级向量，PGVector 够用。上了千万级、纯向量检索成为瓶颈时，再考虑 Milvus 或 Pinecone。选型原则：不要为了"未来可能需要"提前引入复杂度。

### 第 11 题：MySQL 索引优化，举个具体案例？

**回答方式**

用一个真实的慢 SQL 案例——讲当时的场景（哪条 SQL、多慢），explain 看到了什么，加了什么索引，加完效果差多少。

**回答**

蔬蔬买菜订单列表页有一个典型慢查询。场景是运营后台查订单列表，SQL 大致是：

```sql
SELECT * FROM orders 
WHERE user_id = ? AND status = ? AND create_time BETWEEN ? AND ?
ORDER BY create_time DESC
LIMIT 20;
```

explain 发现 type 是 ALL，全表扫了 30 万行。因为表上只有一个 user_id 的单列索引，status 和 create_time 都没走索引，而且 ORDER BY create_time 触发了 filesort。

我建了一个联合索引 `(user_id, status, create_time)`。这个顺序是有讲究的——user_id 是等值查询放最左，status 也是等值查询放第二，create_time 有范围查询也有排序需求放最后，这样索引覆盖了 WHERE 的三列和 ORDER BY 的一列。

建完索引后 explain 显示 type 变 ref，key_len 显示用了全部三列，Extra 里 filesort 消失了。实际查询时间从 2.3 秒降到 50ms 左右，效果明显。

### 第 12 题：Redis 持久化，RDB 和 AOF 你们怎么选的？

**回答方式**

先说两个方案各自的特点（一句话），再说你们用了什么、为什么。最后提一句"有没有遇到数据丢失"——承认遇到过，然后说怎么解决的。

**回答**

RDB 是定期快照——Redis 每隔一段时间把内存数据 dump 到磁盘。优点是恢复快、文件小、对性能影响小。缺点是两次快照之间的数据可能丢。

AOF 是追加日志——每一条写命令都记到文件里。优点是数据更安全（可以每秒刷盘），缺点是文件大、恢复慢。

蔬蔬买菜用的是混合持久化（Redis 4.0+ 的特性）：RDB 做全量快照 + AOF 记录快照期间的增量。这样既有 RDB 的恢复速度，又有 AOF 的数据安全。持久化频率设的是 AOF 每秒 fsync 一次——工程上一个比较平衡的选择，不丢超过 1 秒的数据，对性能影响可控。

数据丢失确实遇到过一次。服务器异常断电，AOF 文件尾部损坏了，Redis 重启失败。排查后发现是刷盘还没完成就断电了，最后用 redis-check-aof 工具修复去掉了不完整的尾部命令，重启恢复。之后加了两件事：一是加了一个定时任务每天备份 AOF 文件到另一台机器，二是在代码层加了缓存穿透保护，Redis 不可用时走数据库兜底。

### 第 13 题：Docker + Serverless 平台怎么用的？

**回答方式**

先说什么 Serverless 平台，再说冷启动延迟怎么处理，最后说 FastAPI 在 Serverless 上和传统部署有什么不同。

**回答**

用的是阿里云函数计算（FC）——把 FastAPI 项目打成 Docker 镜像推到容器镜像仓库，FC 会按请求量自动扩缩容实例。Dockerfile 就是标准的 Python 多阶段构建：第一阶段装依赖，第二阶段只保留运行时需要的最小体积。

冷启动延迟确实是 Serverless 的一个痛点——容器首次启动大概 2-5 秒。我们的处理方式：一是把镜像体积压到最小（不用完整 Linux 镜像，用 python:3.11-slim），启动阶段只加载必需的依赖；二是设了最小保留实例（1 个），保证至少有一个实例始终热启动；三是对 DashScope SDK 这种外部依赖做了初始化延迟加载——不进启动主路径，首次调用时才初始化。

FastAPI 在 Serverless 上跟传统部署有三个不同。第一，传统部署服务是常驻进程，Serverless 是请求来了才启动容器，请求处理完可能很快就被回收——所以服务必须是无状态的，所有状态放 Redis 或数据库。第二，SSE 流式推送到 Serverless 需要特别处理——函数计算默认请求超时 60 秒，长对话会超时，所以我把流式请求的超时单独配到 120 秒。第三，连接池管理——传统部署可以用全局连接池，Serverless 每个实例独立，连接池大小控制在 5 以内避免撑爆数据库连接数。

### 第 15 题：为什么选 PgVector 而不是 Milvus、Weaviate 或 Pinecone？

**回答方式**

**回答**

选 PGVector 的核心原因是场景匹配——KnowOcean 目前十万级向量、单机部署、团队小。

对比四个方案。Milvus：性能最强，分布式架构能撑十亿级向量，但需要独立部署和运维，GPU 加速还要额外配置。对 KnowOcean 当前规模来说太重了。Weaviate：功能全但模型绑定紧，自带向量化模块不够灵活，我更喜欢自己控制 embedding 流程。Pinecone：全托管最省心，但数据不在自己服务器上，且按请求量计费，成本随调用量线性涨——长期来看不如自己维护 PGVector 划算。

PGVector 刚好满足我三个需求：跟业务数据在同一个 PostgreSQL 里，一个库搞定所有存储；会用 PostgreSQL 就会用 PGVector，运维学习成本为零；十万级向量 HNSW 索引查询稳定在 20-50ms，够用。

HNSW 索引参数我设的是 m=16, ef_construction=200。m 控制每层每个节点连多少个邻居——16 是跟 1024 维向量匹配的中等值，连接太多构建慢，太少检索精度降。ef_construction 控制构建时的搜索宽度——200 是精度和构建时间的平衡点。

边界条件：上了千万级向量、纯向量检索成为瓶颈时，会考虑换 Milvus 做纯向量检索层，PGVector 回归做业务数据存储。

### 第 20 题：「支持最多 3 路查询并发检索」，哪三路？

### 第 21 题：RRF 融合同加权求和融合相比，RRF 好在哪？

**回答方式**

一句话说清加权求和的痛点，再说 RRF 怎么解决的。最后坦诚说 Learning to Rank 想过但目前没用。

**回答**

加权求和的痛点：两个通道各自分数的量纲完全不同。PGVector 的余弦相似度是 [-1, 1] 之间的小数，ES 的 BM25 分数可以根据文档长度和词频涨到几十甚至上百。加权求和意味着必须人工设一个权重比例——w1 给 PGVector、w2 给 ES——这个比例极其敏感且依赖数据集。

RRF 不碰原始分数，只看排名。公式是 score = Σ 1/(k + rank)。不管你 PGVector 第一名得分是 0.95 还是 ES 第一名得分是 45，在 RRF 里只看你是第几名。这样就从根本上回避了量纲对齐问题。

Learning to Rank 想过但没做——需要标注训练数据（大量人工标注哪些文档对哪些查询相关），对于独立开发项目来说成本太高。将来如果数据积累够了，会考虑用 xgboost 或 LightGBM 学习 RRF 的 k 值甚至更复杂的特征组合。

### 第 22 题：RAG 系统怎么评估好坏？

**回答方式**

分检索和生成两个层面讲——检索看什么指标、生成看什么指标。坦诚说目前主要是人工 + 部分自动化。

**回答**

目前 KnowOcean 主要是人工评估——准备几十组"问题 → 期望答案"测试对，改了参数或 prompt 后手动跑一遍看效果。

如果要系统化评估，分两层。检索层看两个指标：MRR（平均倒数排名）衡量第一个相关文档的排名，NDCG@5 衡量 Top 5 的整体排序质量。生成层看四个 RAGAS 指标：Faithfulness（答案是否基于检索文档而非模型自己编的）、Answer Relevancy（答案是否切题）、Context Precision（检索的文档里相关文档的排名）、Context Recall（是否找全了所有相关文档）。

具体做法是建一个 Golden Dataset——人工标注 100-200 条查询对应的正确文档和期望答案——作为 ground truth。每次改动后 RAGAS 自动跑四个指标。同时保留人工抽检——自动化评估有时跟人工感受有偏差。

坦白说这是我目前的一个短板——KnowOcean 缺少系统化的评估流水线。如果重做，我会在所有功能开发之前先把评估框架搭好。

### 第 29 题：SSE 连接断了怎么办？Agent 推理到一半出错了怎么处理？

**回答方式**

两个问题分开答——SSE 重连讲前端策略，Agent 容错讲后端兜底。

**回答**

SSE 连接断开：前端用了 EventSource 的自动重连机制——浏览器原生的 EventSource 在连接断开后会自动重试，间隔递增。同时在前端维护了一个"消息 ID"——重连后带上 `Last-Event-ID` header，后端能定位到断点，从该点之后继续推送。如果断开超过 10 秒且重连失败，前端显示"连接已断开，请刷新重试"并保留已收到的部分内容。

Agent 推理到一半出错：分几种情况处理。工具调用失败（知识库无结果、API 超时）→ 有备用工具就走备用，没备用则直接输出兜底话术"当前无法获取该信息"。LLM 返回格式不可解析 → 用正则尝试提取 Action 内容，失败则重试一次，两次失败直接结束本轮回答问题。SSE 推送中途异常 → try-catch 捕获后发送一个 `{"event": "error", "data": "处理中断"}` 的 SSE 事件给前端，前端收到后保留已展示内容并提示。

### 第 30 题：Spring Cloud Alibaba 用了哪些？Nacos、Seata、Sentinel 怎么配的？

**回答方式**

逐一说明每个组件在蔬蔬买菜中的实际用途和配置方式。

**回答**

蔬蔬买菜用了四个核心组件。

Nacos 做注册中心和配置中心。注册中心：微服务启动注解 @EnableDiscoveryClient，注册到 Nacos，服务间用 Feign + 服务名调用，负载均衡走 LoadBalancer。配置中心：数据源配置、Redis 连接、第三方支付 Key 等都放 Nacos，改配置发布后服务自动热刷新。多环境用 namespace 隔离——dev/test/prod 各自独立命名空间。

Gateway 网关：写了鉴权过滤器（验 token）和请求日志过滤器（记录 path + 耗时），所有外部请求统一走 Gateway 再转发到内部微服务。

Seata 做分布式事务——这个等下道题详细讲。

**追问：你自己会搭建一套微服务项目吗？从零开始怎么做？**

**回答方式**

不要只说"会"或"不会"，把搭建过程讲一遍——从创建项目到启动所有服务，让面试官听到你有实操过。按步骤讲，每步一句话说明做什么。

**回答**

会。蔬蔬买菜项目就是我参与搭建的，我走一遍从零开始的完整流程。

第六步，分布式事务。引入 Seata 处理下单流程中的跨服务事务——订单服务扣优惠券、扣库存、生成订单、更新状态，要么全部成功要么全部回滚。用的是 AT 模式，不需要在业务代码里写补偿逻辑。

第七步，启动验证。Docker Compose 编排所有服务——Nacos + Sentinel Dashboard + MySQL + Redis + 各个微服务。启动后看 Nacos 控制台确认所有服务已注册，网关路由测试通了，再跑一遍核心链路确认没问题。

这套流程走完后，一个新的微服务项目就搭起来了，后面就是往里面加业务代码。

### 第 31 题：下单扣库存的分布式事务怎么处理的？

**回答方式**

先说场景——下单涉及订单服务 + 库存服务 + 账户服务，跨三个微服务。再讲 Seata AT 模式的原理，最后说一笔交易的实际执行过程。

**回答**

下单场景涉及三个微服务——订单服务（创建订单）、库存服务（扣库存）、账户服务（扣余额或积分）。这三个操作要么全成功要么全回滚。

用的是 Seata AT 模式。原理简单说就是两阶段——第一阶段各服务执行自己的 SQL（订单 insert、库存 update、账户 update），Seata 自动生成回滚用的 undo log。第二阶段，全部成功则提交（删 undo log），任何一个失败则回滚（用 undo log 反向补偿）。

一笔下单的实际流程：Gateway 接请求 → 订单服务开启全局事务（@GlobalTransactional）→ Feign 调库存服务扣库存 → Feign 调账户服务扣余额 → 全部返回成功 → Seata TC 发全局提交。如果库存扣减失败返回异常，Seata TC 发全局回滚，订单服务删掉已创建的订单，库存服务恢复已扣的数量。

### 第 32 题：为什么用 Shiro 而不是 Spring Security？

**回答方式**

给出当时的选型理由——团队熟悉度、轻量、RBAC 契合。然后讲 Shiro RBAC 的表结构设计。

**回答**

当时的考量几个点。团队对 Shiro 更熟悉——之前的项目一直用 Shiro，迁移成本低。Shiro 比 Spring Security 轻——配 RBAC 权限几行代码搞定的场景，Spring Security 要写整块配置类。而且项目不需要 OAuth2、LDAP 这种复杂认证，Shiro 的 Session + Token 完全够用。没有"Shiro 比 Security 好"的意思，是当时那个场景下最合适的选择。

RBAC 表结构是标准的五张表：user（用户）、role（角色）、permission（权限）、user_role（用户-角色关联）、role_permission（角色-权限关联）。权限粒度是三级——角色级决定能进哪些菜单、菜单级决定能看到哪些页面、接口级决定能调哪些 API。

接口级权限的实现用了 Shiro 的 @RequiresPermissions 注解，在 Controller 方法上加注解配合 AOP 自动校验当前用户的角色是否有对应权限。权限数据存 MySQL，用户登录时加载一次后缓存在 Redis，Token 有效期 2 小时。

### 第 33 题：抽奖活动高并发下怎么防超卖？

**回答方式**

讲 Redis + 分布式锁的组合方案。先给核心思路，再说具体实现。

**回答**

抽奖场景的核心问题是奖品数量有限、高并发下多个用户同时抽可能超卖。

核心方案是用 Redis 做奖品库存计数 + Redisson 分布式锁做扣减互斥。具体流程：用户点抽奖 → 去 Redis 查这个奖品的剩余库存（一个 key，存剩余数量）→ 大于 0 才进入抽奖逻辑 → 用 Redisson 分布式锁锁住这个奖品 → 在锁内再做一次库存检查（双重检查）→ 扣库存 → 释放锁 → 抽奖结果入异步队列写数据库。

为什么不用数据库行锁？数据库行锁在高并发下会造成大量等待和超时，Redis 的原子操作（decr）性能高出几个数量级。为什么加分布式锁还要双重检查？因为查库存和扣库存之间有时间窗口，锁内双重检查是最后一道防线——99.9% 的并发情况 Redis decr 本身就能挡住，这 0.1% 是兜底。

红包金额防超发类似——总预算在 Redis 里实时递减，发到一个阈值（比如预算剩余 5%）停止并发直接转为先到先得。

### 第 34 题：为什么用 MongoDB 的地理索引而不是 MySQL 的空间索引或 Redis GEO？

**回答方式**

三个方案对比，说清为什么选 MongoDB。不贬低另两个，只说场景匹配。

**回答**

三个方案各有优劣。

MySQL 8.0 的空间索引用的是 R 树，做"点在不在多边形内"这种查询理论上是支持的。但当时用的是 MySQL 5.7（空间索引支持不如 8.0 完善），而且配送区域数据是 GeoJSON 格式——MongoDB 对这种格式的原生支持更好，存进去就能建 2dsphere 索引直接查询，不需要做格式转换。

Redis GEO 的底层是 ZSET + Geohash，做"附近 XX 公里内"这种圆形范围查询非常快。但蔬蔬买菜的场景是平台自定义的不规则配送区域（一个商家覆盖几个小区但不到另一个），不是简单的"半径 N 公里"——GEO 做不了多边形覆盖判断。MongoDB 的 2dsphere + GeoJsonPolygon 原生支持这个。

所以 MongoDB 刚好卡在 MySQL 和 Redis 都覆盖不到的位置——既要支持不规则多边形的地理查询，又要有文档型数据库的灵活性来存配送区域的复杂结构。

### 第 35 题：POI 大数据量 Excel 导出会不会 OOM？

**回答方式**

先说原生 POI 会 OOM 的原因（DOM 模式全部加载到内存），再讲 EasyExcel 的 SAX 流式原理解决 OOM。导入和导出分开讲，导入强调多线程解析 + 批量插入，导出强调分页查询 + 边查边写。最后补百万级以上数据量的兜底方案（多文件打包 / CSV）。

**回答**

用原生 Apache POI 做百万数据导出，答案是：一定会 OOM。因为 POI 的 XSSFWorkbook 是 DOM 模式——在写入文件之前，会在内存里构建一个完整的 Workbook 对象树，所有行、单元格、样式全部加载到堆里，一次性写入。几十万行就扛不住了，百万行必 OOM。

生产环境的主流方案是用阿里 EasyExcel。它底层基于 POI 的 SAX 模式，不是把所有数据攒到内存再写，而是流式写入——每攒到一定行数就 flush 到磁盘临时文件，只保留轻量上下文在内存里，最终再合并输出。内存峰值可以控制在几十 MB，百万数据完全没问题。

导入和导出策略不同：

导入方面，数据量大时用多线程解析。每个 Sheet 分配一个独立线程，用 EasyExcel 的 SAX 监听器逐行读取，解析完的行放入一个阻塞队列，另一个线程池从队列消费，攒够一定条数（比如 500 条）就一次 batch insert 写库。核心思路是解析和入库解耦，互不阻塞，也不会把数据库连接打满。

导出方面，用分页查询 + 边查边写。每次从数据库查几千条，查完立刻写入，不积压数据。核心代码结构：先构建一个 ExcelWriter，然后循环分页，每次 queryPage 查一页数据，直接 writer.write 写入一个 Sheet。所有页写完再 finish 关闭。如果数据量大到需要拆多个文件（比如千万级），就按业务维度拆成多个文件打包成 zip 下载。

几个工程细节也很关键：样式要复用——定义一个静态 Map 缓存 CellStyle，不要每行都 new，否则样式本身就把内存撑爆了。导出操作走异步——先返回任务 ID，后台线程处理，完成后发通知或轮询下载。同一用户限流防重入——用 Redis 锁控制同一时间只允许一个导出任务。最后设置超时机制，超时自动释放资源。

总结下来核心就一句话：不用 DOM 一把梭，改成流式处理 + 分页分片，配合限流兜底，千万级也能撑住。

**可能的追问**

**追问 1：EasyExcel 和 POI 原生的 SXSSFWorkbook 什么关系？为什么不直接用 SXSSFWorkbook？**

**回答方式**

先说两者关系——EasyExcel 底层就是基于 POI 的 SXSSFWorkbook 实现的，但做了更高层的封装，让调用方不用关心流式写入的细节。然后对比两者的差异——SXSSF 用起来更底层、需要自己管理临时文件和行窗口，EasyExcel 提供了更友好的 API 和更完善的内存控制。

**回答**

EasyExcel 底层确实就是基于 POI 的 SXSSFWorkbook 实现的。SXSSF 是 POI 3.8 之后提供的流式写入版本——它不会在内存里构建全部行对象，而是维护一个可滚动行窗口（默认 100 行），超过窗口的行 flush 到磁盘临时文件。

那为什么不直接用 SXSSF？因为 SXSSF 虽然解决了 OOM，但用起来有很多细节要自己处理。比如临时文件清理——SXSSFWorkbook 用完不手动 dispose，临时文件不会自动清理。再比如写入性能调优——rowAccessWindowSize 设多少、什么时候调 flush、样式怎么复用，这些都要自己踩坑。EasyExcel 等于把这些底层细节封装掉了，对开发者来说就是定义一个监听器、调一个 write 方法，心智负担小很多。

如果你对 POI 很熟、需要高度定制的写入行为（比如做复杂的报表模板），直接上 SXSSF 也是合理选择。但大部分业务场景 EasyExcel 是更稳妥的选项。

---

**追问 2：你说的分批写，具体多少条 flush 一次？这个参数怎么定的？**

**回答方式**

给一个具体的数值和推导逻辑，不要说背的，要说根据什么场景测出来的。

**回答**

EasyExcel 底层 SXSSFWorkbook 默认窗口是 100 行，但实际业务中我一般设 5000~10000 行 flush 一次。原因是频率切得太细（比如 100 行 flush 一次）会导致频繁 IO，写入总时长反而变长。设得太粗（比如 50000 行）又会有阶段性的内存冲高，违背流式写入的初衷。

我调试时做过一次对比测试：导 50 万行数据，设 1000 行 flush 一次总耗时约 38 秒，设 5000 行约 25 秒，设 10000 行约 22 秒，设 50000 行约 21 秒但内存峰值高了 80MB。最后选了 5000 行作为平衡点——写入时间跟 10000 行差距不大，但内存安全裕度大很多。

这个值不是固定的——字段数多的宽表就调小一点（行对象本身占内存），字段数少的窄表就调大一点。

---

**追问 3：如果导出的行数超过了 .xlsx 的单 Sheet 上限（104 万行），你怎么处理？**

**回答方式**

分三个方案递进——自动拆 Sheet、按业务维度拆文件、换 CSV。先说各自场景，再说怎么选。

**回答**

三个方案，按场景选。

第一，按固定行数自动拆 Sheet。EasyExcel 写入时计数，当前 Sheet 达到 104 万行就自动新建一个 Sheet 继续写。优点是实现简单，对调用方透明；缺点是用户拿到一个文件多个 Sheet，体验上不太方便。

第二，如果数据本身有业务维度（比如按月份、按省份、按商家），更推荐按维度拆成多个独立文件，打包成一个 zip 下载。比如导出全年订单，按月拆成 12 个 .xlsx 文件再压缩。优点是每个文件对用户来说有意义，下载和使用都方便。

第三，如果数据量到了千万级甚至上亿，直接用 CSV。CSV 没有行数上限，写入就是 IO 流，不存在 OOM 问题。代价是不能带格式、图片、公式，适合数据量大但格式要求低的场景。

选型原则：能给用户分就别让用户自己筛，能给用户有意义的单元就别给一个大而全的单文件。

---

**追问 4：导入时多线程解析 + 批量插入，有没有遇到数据顺序错乱的问题？线程池参数怎么设的？**

**回答方式**

先说顺序问题怎么解决的（带行号排序 / CompletableFuture 有序消费），再说线程池参数的推导逻辑。

**回答**

顺序问题分两个层面。第一个是 Sheet 内部的顺序：如果一个 Sheet 内的行有父子依赖关系（比如订单头 + 订单明细），就不能乱序插入。方案是解析行时带上行号，消费线程按行号排序后批量写入。第二个是跨 Sheet 的顺序：如果 Sheet A 和 Sheet B 之间没有依赖关系，那乱序也没关系。有依赖的话就按 Sheet 维度串行消费。

线程池参数我是这么设的：核心线程数设 CPU 核数（解析是 CPU 密集型），最大线程数设 CPU 核数 * 2，队列容量设为能容纳一个完整 Sheet 的总行数。数据库批量插入的线程池单独配——核心线程数设数据库连接池大小的一半（比如连接池 20，插入线程就设 10）。

不能把解析线程和插入线程混用一个线程池。解析是 CPU 密集型，插入是 IO 密集型，分开配资源利用率更高。

---

**追问 5：用户点了导出嫌慢又点了一次，会不会同时跑两个导出任务？怎么防？**

**回答方式**

先说问题——不加控制的确会重复跑，浪费资源。再说方案——分布式锁防重入 + 前端按钮防连点，两层兜底。

**回答**

会。不加控制的话用户点两次就启两个导出线程，挤占数据库连接和服务线程资源。

前后端两层防。后端用 Redis 分布式锁，key 设计为 export:lock:{userId}:{exportType}，加锁时设过期时间（比如 5 分钟，超时自动解锁防止死锁）。如果第二个请求来的时候锁还在，直接返回"您有一个正在进行的导出任务，请稍后再试"。

前端也做一层防御：用户点击导出按钮后，按钮置灰并显示"导出中..."，disable 掉直到请求完成或失败。这是用户体验层面的兜底，但后端锁才是真正可靠的——前端能绕过（比如用户直接调 API）。

---

**追问 6：导出到一半用户关了浏览器，后台任务还在跑吗？怎么处理？**

**回答方式**

先承认这个问题确实存在，然后讲三种处理方式及其成本收益。

**回答**

用户关了浏览器，后台任务不一定感知得到——HTTP 是请求-响应模式，服务器不会因为客户端断开就自动终止线程。所以后台任务可能继续跑完，把文件生成好放在服务器上，但用户永远拿不到了。

三种处理方式。

第一种（最简单）：不管，文件放服务器上设置 TTL（比如 30 分钟），超时自动清理。浪费一点计算资源但实现成本最低。

第二种：后台轮询检查任务状态。每次导出任务开始时记录一个 Task 状态到 Redis，前端通过 SSE 或轮询获取进度。如果前端连续几次轮询没返回（超时），判定用户断开，后端发送中断信号给导出线程。实现相对复杂，但能及时释放资源。

第三种（折中）：文件生成完后检查是否还有人在等。用数据库或 Redis 记录该导出任务的最后一个 SSE 心跳时间。如果生成完文件时心跳已经断了，就直接删文件不留垃圾。

大部分生产系统用的是第一种——省事，配合下班前的定时清理脚本就行。毕竟导出任务本身是低频操作，浪费的资源有限。

---

**追问 7：如果导出的 Excel 还要带复杂格式（合并单元格、条件格式、图片、数据透视表），EasyExcel 还能搞定吗？**

**回答方式**

先说 EasyExcel 的能力边界——它擅长什么、不擅长什么。再说大数据量复杂报表的场景下怎么做。

**回答**

EasyExcel 擅长的是大数据量的"规则表格"——表头固定、每行结构相同、不带复杂格式。对于合并单元格、图片嵌入、条件格式这些场景，EasyExcel 能做但不太好做，API 不如原生 POI 灵活。数据透视表更是超出了 EasyExcel 的设计范围。

如果业务确实需要带复杂格式的大文件导出，有两个方向。

方向一是模板填充。用 Excel 编辑器先画好模板（含合并单元格、条件格式、公式），用 EasyExcel 的 fill 方法往模板里填充数据行，循环填充完。模板什么样，导出就什么样。

方向二是先用 EasyExcel 写数据，再用 POI 的底层 API 打开已生成的文件后处理——追加合并单元格、设置条件格式等。两个工具接力完成，各取其长。

但如果同时要满足"百万行"和"每行带图片"这两个条件，就应该重新审视需求了——是不是前端生成更合理？是不是图片应该转成链接而不是嵌入到单元格里？

**追问 8：百万数据导出一般多长时间？用户等不了这么久怎么办？**

**回答方式**

先给一个你实际遇到的数字，再讲异步导出的完整链路（包括进度反馈）。

**回答**

50 万行、10 列左右的表，用分页查询 + EasyExcel 写入，大约需要 20~30 秒。百万行在 40~60 秒左右，具体取决于数据库查询效率和字段数量。

让用户等一分钟是不现实的，所以大导出必须走异步。流程是：用户点击导出 -> 后端创建导出任务，返回 taskId -> 后台线程处理 -> 处理完后文件上传到 OSS 或存本地 -> 通过 SSE 或 WebSocket 推送导出完成通知给用户 -> 用户拿到下载链接直接下载。

进度反馈：导出过程分成"查询第 1/20 页 -> 写入"等多个阶段，用 Redis 更新任务进度百分比，前端通过轮询或 SSE 实时展示进度条。用户能看到"正在导出，已处理 35%"，焦虑感会小很多。

还有一个取巧的做法：第一页数据查出来就生成第一个 Sheet 并推送部分可下载链接，用户可以先下载已生成的部分，后面的后台继续追加。不过这在大导出场景里用得少，一般都是等全部完成再给链接。

## 十二、AI 专项深度追问（13 题）

### 第 38 题：Tool Calling 的具体实现——tool schema 怎么定义？LLM 输出错误参数怎么兜底？多个 tool 时 Agent 怎么选？

**回答方式**

先讲 tool schema 的定义格式，再说容错机制的两层设计，最后讲 tool 选择是 LLM 自己做决策而非代码路由。

**回答**

在 KnowOcean 里，每个 tool 用 JSON Schema 定义，包含 name、description、parameters（类型、必填/可选、约束条件）。description 是最关键的——它决定了 LLM 能不能正确理解什么时候该用这个 tool。我写 description 的原则是：像文档一样精确，说清楚"这个工具干什么、参数是什么、返回值什么格式、什么时候用"。比如 kb_search 的 description 是"在知识库中检索与查询相关的文档片段，返回 Top 5 最相关的 chunk 及其来源信息。当用户的问题可能在知识库文档中有答案时使用此工具"。

兜底分两层。第一层是参数校验——LLM 返回的 tool call 参数先过一遍 Pydantic 校验，类型不对或缺少必填字段直接拦截，返回一个错误提示让 LLM 重试。第二层是执行容错——工具调用成功但返回空结果也算正常（可能确实没相关知识），但如果是超时或异常，则返回一个结构化的 error 给 LLM，让它决定换策略还是给兜底回答。

多个 tool 时 Agent 怎么选？我的做法不是在代码里做路由，而是在 system prompt 里列出所有可用 tool 的 description，让 LLM 自己做决策。LLM 会根据当前 Thought 判断"我最需要什么信息？哪个 tool 能给我这个信息？"。如果 LLM 选错了，Observation 回来发现信息不对口，下一轮它会自己换一个 tool。这个选择能力取决于 tool description 的质量——description 写得越清晰，LLM 选得越准。

**追问：Agent 调用工具的完整执行流程是什么样的？**

**回答方式**

按时间线走一遍完整的 ReAct 循环——从用户提问到最终回答，每一步做了什么。再说 Native Function Calling 和 Prompt-based 两种模式的区别。

**回答**

完整的 ReAct 循环分五步。

第一步，组装 System Prompt。把 Agent 的角色定义、可用工具列表（每个工具的 name、description、parameters 的 JSON Schema）、对话历史、检索结果拼成一个完整的 system message。工具列表是关键——LLM 看到哪些工具可用，才知道遇到什么问题该调什么工具。

第二步，LLM 推理生成 Thought 和 Action。LLM 看完 system prompt 和用户问题后，输出一个 ReAct 格式的文本。Thought 是推理过程（"用户问的是某个 API 的用法，我应该先去知识库检索相关文档"），Action 是工具调用指令（工具名 + 参数）。这一步有两种模式：Native Function Calling 模式（LLM API 原生支持 tool 参数，直接返回结构化的 tool_call 对象，不需要 LLM 自己写 JSON）和 Prompt-based 模式（在 prompt 里给格式示例，让 LLM 自己输出 JSON 格式的 Action，再正则提取解析）。KnowOcean 用的是 Prompt-based 模式，因为当时选型的模型对 Function Calling 支持不完善，而且希望 Agent 的推理过程在 Thought 中完整可见，方便调试。

第三步，解析 Action 并执行工具。解析出工具名和参数后先过 Pydantic 校验——类型不对或缺少必填字段就返回错误让 LLM 重试。校验通过后调用对应的工具函数（如 kb_search、calculator、memory_search）。工具执行结果格式化为 Observation，拼回对话上下文。

第四步，将 Observation 作为新消息发给 LLM，让 LLM 继续推理。LLM 看到 Observation 后可能有两种决策：如果信息还不够，继续输出 Thought + Action 调下一个工具；如果信息足够了，输出 Final Answer 结束循环。循环终止条件：LLM 输出 Final Answer、达到最大迭代次数（一般设 5-10 轮）、或 LLM 输出明确的"无法回答"标记。

第五步，生成最终回答。LLM 决定不再调工具后，输出最终答案。如果是 SSE 流式场景，这一步把 token 逐个推送到前端。

几个关键设计细节：一是循环必须有最大轮次限制——防止 Agent 无限循环调工具，碰到复杂问题应在 5-8 轮后给出当前已有信息的部分回答。二是每个工具调用的结果要结构化——不要光秃秃的字符串，要带上来源、置信度等元信息，让 LLM 能判断结果质量。三是如果 LLM 连续两次调同一个工具且参数相同，说明它在原地打转——应该主动打断并给兜底回答。

在 KnowOcean 里这套循环用 Python asyncio 实现异步非阻塞执行——一个 Agent 循环中可能调多次 kb_search（每次几十毫秒），异步可以让这些调用不阻塞事件循环，保持 SSE 推送的实时性。



### 第 39 题：LLM 参数调优——temperature、top_p 怎么设？Agent 思考和最终回答用同一套参数吗？

**回答方式**

分场景讲参数设置，核心是"Agent 思考留一点创造性，最终回答要绝对稳定"。

**回答**

Agent 思考和最终回答用的是不同的参数。Agent 的 Thought/Action 阶段 temperature 设为 0.3——需要一定的创造性和探索空间（比如判断调哪个 tool、怎么组织查询语句），但不能太高否则会乱调 tool 或输出格式不可解析。最终回答阶段 temperature 设为 0.1——这时候需要稳定、准确、忠实于检索文档的输出，创造性反而有害（容易编造内容）。

其他参数：top_p 保持默认 0.8 没特别调，因为 temperature 已经控制了随机性；max_tokens 根据阶段不同——Thought/Action 阶段限制 500 token（思考不需要太长），最终回答阶段放开到 2000 token（容许详细的引用和解释）。

经验：知识库问答这种场景，宁可使用低 temperature 配多次采样，也不要高 temperature 一次出结果。低 temperature 答案质量更可控，幻觉明显减少。

### 第 40 题：Token 计算和上下文裁剪——怎么算 token？除了摘要压缩还有别的裁剪策略吗？

**回答方式**

先说 token 计算用的什么工具、为什么不能混用 tokenizer，再说多层裁剪策略和裁剪顺序原则。

**回答**

Token 计算用的是 DashScope SDK 自带的 token 计数功能，底层是 qwen 系列专用的 tokenizer。不能用 tiktoken（那是 OpenAI 的），不同模型的 tokenizer 算出来不一样。每次请求前都会算一遍当前上下文的总 token 数——包括 system prompt + 历史摘要 + 近期对话 + 检索结果 + 当前用户问题。

除了摘要压缩，还有三层裁剪。第一层是检索结果截断——如果 Top 5 检索结果加起来超过 3000 token，按证据评估等级截断，只保留 SUFFICIENT 和 PARTIAL 的 chunk，WEAK 和 NONE 不进 prompt。第二层是对话历史截断——如果近期轮次加上压缩摘要还是超了，优先保留最近 2 轮完整对话，中间的先剪掉（已经反映在摘要里了）。第三层是 system prompt 拆分——把 system prompt 分静态部分（固定角色定义）和动态部分（可用 tool 列表、当前上下文），超限时只保留静态部分。

总结裁剪原则：先剪"可恢复"的信息（检索结果可以从库再取、历史对话有摘要），不剪"不可恢复"的信息（用户当前问题、system prompt 核心约束）。

### 第 41 题：AI 应用的可观测性——LLM 调用的延迟、成功率、token 消耗怎么监控？

**回答方式**

先说当前项目的监控情况（坦诚说比较简单），再说如果产品化会加的三层监控。

**回答**

坦率说，KnowOcean 目前的可观测性比较简单——日志层面记录了每次 LLM 调用的耗时、token 消耗和返回状态码。排查问题主要靠看日志。

如果产品化，会加三层监控。第一层指标采集——每次 LLM 调用记录 model_name、prompt_tokens、completion_tokens、latency_ms、status（success/error/timeout），写入 Prometheus。第二层仪表盘——Grafana 看实时 QPS、P50/P99 延迟、错误率、每小时 token 消耗趋势。第三层告警——错误率超过 5% 或 P99 延迟超过 5 秒自动告警通知。

最关键的一个指标是 token 消耗趋势——因为模型 API 是最大的可变成本，token 消耗突然飙升可能意味着 prompt 被污染、对话循环或检索结果爆炸，要比延迟和错误率更早发现问题。

### 第 42 题：LangChain 的使用边界和踩坑——用了哪些模块？踩过什么坑？有没有想过不用？

**回答方式**

不回避踩坑，诚实讲使用范围、具体踩坑经历、以及"渐进式脱离"的策略。

**回答**

KnowOcean 里 LangChain 主要用于三个地方：AgentExecutor 管理 ReAct 循环、ConversationBufferMemory 做对话上下文管理、以及部分 Chain 做文档加载和文本分割。不是所有模块都用 LangChain——混合检索、RRF 融合、证据评估这些核心逻辑都是自己写的。

踩过最典型的坑是链式调用出错时的报错信息——LangChain 的异常层层包装，一次 Agent 调用失败可能抛出四五层嵌套的异常，根本看不出是哪层哪个参数传错了，只能看源码定位。还有版本升级带来的 breaking change——从 0.1.x 升到 0.2.x 时有些类名和导入路径变了，旧代码直接跑不起来。

我的策略是「渐进式脱离」——初期用 LangChain 快速跑通 MVP（它帮我省了大量样板代码），后期对性能和稳定性敏感的模块逐步替换成自己的实现。比如 Memory 模块最早用 LangChain 的 ConversationBufferMemory，后来发现它的摘要压缩太简单（就是 truncate 最老的消息），于是自己写了 Compact Summary + Hook 动态注入这套体系。LangChain 是梯子不是拐杖——用它加速启动，但不依赖它一辈子。

### 第 43 题：结构化输出——怎么让 LLM 稳定输出可解析的 JSON？

**回答方式**

Agent 的 Thought-Action 格式和证据评估的结果都依赖 JSON 解析，讲三个手段——Few-shot 示例、Pydantic 校验、多级容错。

**回答**

三个手段。第一，prompt 里给明确的格式示例。不是只说"输出 JSON"，而是在 system prompt 里给 2-3 个完整的输入输出示例，格式就是期望的样子。LLM 非常擅长模仿格式——Few-shot 示例比任何格式约束指令都有效。

第二，用 Pydantic 做输出校验。LLM 返回的 JSON 先经过 Pydantic 模型校验——字段缺失、类型不对、extra 字段都会当场报错。校验失败的走重试逻辑——把错误信息作为新的 Observation 反馈给 LLM，"你上次输出的 JSON 缺少必填字段 action，请重新输出完整格式"。

第三，多级容错。JSON 解析失败先试正则提取——有时 LLM 会把 JSON 包在 markdown 代码块里（\`\`\`json ... \`\`\`），正则把内容抠出来再解析。正则也失败再用一次 LLM 调用做"格式修复"——让 LLM 把格式不规范的输出重新整理成标准 JSON。两次修复都失败才放弃当前轮。

经验：不要指望 LLM 100% 输出正确 JSON，把它当概率事件——80% 的情况是对的，剩下 20% 靠校验+重试+正则修复兜底。

### 第 44 题：GraphRAG 和知识图谱——了解吗？跟你现在的方案比有什么不同？什么场景该用？

**回答方式**

先说出你对 GraphRAG 的理解（展示技术视野），再说跟 KnowOcean 方案的对比和适用场景判断。

**回答**

GraphRAG 是微软 2024 年提出的方案，核心思想是在传统 RAG 的"文档-段落"检索之外，加一层知识图谱的实体关系推理。传统 RAG 检索是"找到包含关键词的段落"，GraphRAG 能做到"查询实体 A 时，顺着图的边找到实体 B 和 C，发现 A→B→C 这条关系链"。

跟我现在的方案对比：KnowOcean 是传统的 chunk-based RAG——文档切块→向量检索→返回相关段落。优势是实现简单、通用性好、对任意文档都适用。劣势是跨段落的推理能力弱——如果答案需要综合多个段落各自提到的不完整信息做推理，纯向量检索很难覆盖。

什么场景该用 GraphRAG：文档之间有明确的实体和关系（比如人物关系、组织架构、技术依赖链），答案需要多步推理才能得出。什么场景不需要：大部分知识库问答是"找相关段落→提取答案"，不需要图推理。我的判断是 GraphRAG 和传统 RAG 是互补不是替代——可以在现有的 RAG 上叠加实体提取和图检索作为增强通道和 PGVector + ES 一起走三路融合。

### 第 45 题：多模态 RAG——PDF 里的图片和表格怎么处理？

**回答方式**

坦诚说当前只处理文本，然后说图片和表格的处理思路——"翻译成文本再走文本 RAG"的取巧做法。

**回答**

坦率说，KnowOcean 目前的 ETL 只处理了 PDF 中的文本层——用 PyMuPDF 提取纯文本内容，图片和表格是被跳过的。如果 PDF 页面是扫描件（纯图片），目前的方案是直接标记为"不支持"返回给用户。

如果要支持图片，思路是：PDF 解析时检测到图片区域 → 截取图像 → 调多模态 LLM（如 qwen-vl）做图片描述生成 → 把描述文本拼到原文档上下文中作为该 chunk 的额外字段。表格类似——检测到表格区域 → 调表格识别模型 → 结构化提取成文本或 JSON → 拼入 chunk。

这也是一种取巧的做法——不是直接做多模态 embedding 和检索（那是更复杂的一套系统），而是把图片和表格"翻译"成文本，然后统一走文本 RAG 流程。代价是会丢失部分视觉信息（如图表的趋势形状），但工程复杂度可控。

### 第 46 题：Fallback 和降级策略——LLM API 挂了怎么办？有没有本地小模型兜底？

**回答方式**

分层降级策略，从"完美路径"到"兜底保底"逐层讲，最后一层坦诚说目前没有本地模型。

**回答**

KnowOcean 的降级分三层。第一层是模型降级——DashScope 的 qwen-max 是主力，如果 qwen-max 超时或报错，自动切换到 qwen-turbo。turbo 质量稍差但速度更快、可用性一样，对绝大多数知识库问答场景质量损失不大。

第二层是功能降级——如果 DashScope 整体不可用（概率极低），Agent 模式降级为纯检索模式：跳过 Query Planning、跳过 Agent 推理，直接把用户问题做关键词+向量检索，把 Top 3 结果的原文片段返回给用户。虽然不是智能回答，但至少用户能看到相关文档。

第三层是人工兜底——如果整个 AI 链路都不通了，返回预设的兜底文案"系统暂时无法处理您的问题，请稍后重试"。目前没有接本地小模型作兜底，主要原因是可用的小模型（如 qwen-1.8B）质量差距太大，兜底体验反而可能比"直接说明不可用"更差。如果未来团队有资源，会在自有服务器上部署一个量化版的中等模型（如 qwen-7B）做真正有意义的降级。

### 第 47 题：Fine-tuning vs RAG——什么场景该微调模型而不是继续优化 RAG？

**回答方式**

给一个清晰的判断框架（三个维度），不要站队。最后给出自己的结论——RAG 为主，微调为增强。

**回答**

判断标准三个维度。第一，知识更新频率。知识库里的文档会不会频繁变动？如果每天都有新文档、旧文档更新，RAG 更合适——改向量库就行不用重新训练。微调适合知识相对静态的场景（比如医学知识、法律法规），模型"内化"了领域知识后回答更流畅更准确。

第二，任务类型。如果任务是"在给定文档中找答案"——天然适合 RAG，因为答案就在文档里。如果任务是"用特定风格、特定领域知识来回答问题"——微调可能更合适，因为这不是检索问题而是风格和知识内化问题。

第三，资源投入。微调需要高质量标注数据（几百到几千条高质量的问答对）和 GPU 训练资源，RAG 只需要建好知识库和检索系统。对于 KnowOcean 这种企业知识库场景，RAG 天然更匹配——文档持续更新、答案分散在不同文档中、微调数据难以维护。我的判断是：绝大多数企业 AI 应用应该以 RAG 为主，微调作为特定场景的增强手段，不是二选一而是组合使用。

### 第 48 题：Prompt 版本管理和测试——prompt 改了怎么知道改好了还是改坏了？

**回答方式**

从当前做法说到理想方案。当前做法朴素但诚实，理想方案展现工程化思维。

**回答**

目前 KnowOcean 的做法比较朴素——改 prompt 之前在本地跑十几条固定的测试查询，对比新旧 prompt 的结果。好的改动是"原来答错的现在答对了"，坏的改动是"原来答对的现在答错了"，都记在笔记里。

如果要系统化，会做三件事。第一，Prompt 纳入 Git 管理——一个独立的 prompts/ 目录，每个 prompt 一个文件，改了什么、谁改的、什么时候改的，全有记录。第二，建 Regression Test Suite——准备 50 条基准测试查询，每条有期望的答案要点（不是整段答案，是"答案中必须包含 XX 信息"这种可自动判定的标准）。第三，每次改 prompt 自动跑一遍 suite，输出"新增通过数"和"新增失败数（回退数）"。如果回退数超过阈值，自动阻断合并。

核心原则：改 prompt 跟改代码一样，必须有测试保护。没有测试的 prompt 优化是盲优化，可能某个 case 变好了但十个 case 变差了。

### 第 49 题：大模型幻觉的工程化解决方案——证据评估之外还有什么手段？

**回答方式**

从 KnowOcean 已有的三层方案说起，再延伸到业界更多手段，最后给出自己想加的下一个方案。

**回答**

KnowOcean 里对抗幻觉的三层方案。第一层是前文讲过的证据评估——检索结果分为 NONE/WEAK/PARTIAL/SUFFICIENT 四级，SUFFICIENT 才正常生成答案，PARTIAL 就加免责声明"以下信息可能不完整"，WEAK 降级为"根据已有信息无法确定"，NONE 直接拒答。这是从源头切断幻觉。

第二层是引文约束——生成答案时要求 LLM 对每个陈述标注引用来源（来自哪个文档的哪个 chunk）。这样有两个效果：一是 LLM 知道自己的答案要被溯源，更倾向于只说检索到的东西；二是用户可以看到每个信息的出处，自行判断可信度。

第三层是 system prompt 约束——明确指令"只基于以下检索到的文档内容回答，不要使用你的训练数据中的知识。如果文档中没有相关信息，请明确说'未找到相关信息'，不要猜测或编造"。

业界还有更多手段。SelfCheckGPT——让 LLM 生成多个候选答案，然后比较它们之间的一致性，不一致的地方大概率是幻觉。但多次生成代价大。Fact-checking 校验 LLM——用一个独立的校验 prompt 检查最终答案的每个事实陈述是否能在检索文档中找到支撑，找不到的标记为"潜在幻觉"。这个是性价比比较高的方案，也是我下一步想加的——在 SSE 推送给用户之前，后台异步跑一遍校验。如果发现幻觉率高，自动在答案末尾追加"注意：以上内容可能包含不确定信息"的提示。



### 第 50 题：什么是 SSE？为什么 AI 应用接口选择 SSE 而不是 WebSocket？

**回答方式**

先说 SSE 的定义和核心特点（单向、HTTP、流式），再跟 WebSocket 做对比（双向 vs 单向、复杂度 vs 简洁性）。最后落到 AI 场景的具体原因——流式生成天然就是单向的，SSE 是刚好够用的方案。

**回答**

SSE（Server-Sent Events）是 HTML5 规范中的一种服务器推送技术。客户端通过 EventSource API 建立一个 HTTP 连接，服务端可以持续向客户端推送文本数据。它是单向的——只能服务端主动推，客户端不能通过这个连接发送数据。数据格式是纯文本的 event stream，每条消息以 data: 开头，以双换行符结束，支持自定义 event 类型和消息 ID。

WebSocket 是另一种通信协议，它是全双工的——建立连接后客户端和服务端可以互相主动发送数据。这比 SSE 更强大但也更重：需要额外的握手升级（HTTP Upgrade 101）、需要自己实现心跳保活、需要处理二进制帧，对负载均衡器、防火墙的配置要求也更高。

AI 应用选 SSE 而不是 WebSocket，核心原因是：LLM 的流式响应是天然单向的。用户发一个问题，服务端流式吐出 token，这个场景里服务端到客户端是数据流，客户端到服务端只是一个请求，没有双向高频通信的需求。SSE 刚好覆盖这个场景，而且：

第一，实现简单。SSE 基于标准 HTTP，不需要协议升级。后端就是普通的 HTTP 响应，设置 Content-Type: text/event-stream 和 Cache-Control: no-cache，然后不断 res.write() 推送数据即可。前端用浏览器原生的 EventSource API，几行代码就能接入，不需要引入任何第三方库。

第二，自动重连。EventSource 在连接断开后会自动重试，间隔递增。WebSocket 需要自己实现重连逻辑——监听 onclose、onerror，写指数退避算法。SSE 这个功能开箱即用，在弱网环境下体验明显更好。

第三，兼容性好。SSE 走标准 HTTP 协议，Nginx、SLB、ALB 不需要额外配置就能支持（只需要关掉 proxy_buffering）。WebSocket 需要负载均衡器显式支持 Upgrade 握手，有些老版本代理会直接拦截。对于部署在 Docker Compose 或 Kubernetes 上的应用，SSE 的配置成本低得多。

第四，资源更轻。SSE 是纯文本传输，没有 WebSocket 的二进制帧解析开销。每个 SSE 连接就是一个普通的 HTTP 长连接，服务端不需要维护复杂的连接状态机。这对于需要同时维持大量用户连接的 AI 应用来说，资源消耗优势明显。

那什么场景该用 WebSocket？需要客户端和服务端频繁双向通信的时候——比如聊天室（用户收发消息都是频率密集的）、实时协作编辑（多人同时修改文档）。AI 对话场景里，用户发一条消息、服务端流式回复，通信模式是典型的“请求-流式响应”，SSE 是刚好够用且最简洁的方案。

总结：选 SSE 不是因为 WebSocket 不好，而是因为 AI 对话的通信模式天然匹配 SSE 的单向流式特性。不做过度设计——能用一个 HTTP 请求解决的问题，就不需要升级到全双工协议。

### 第 51 题：当前单机 Docker Compose，要支撑 1000 个企业用户怎么演进？

**回答方式**

分三步演进——服务拆分、存储升级、接入层改造，每步说清楚"什么变了"和"为什么"。

**回答**

当前 KnowOcean 是单机 Docker Compose 部署（一台 ECS 跑所有服务），如果要支撑 1000 个企业用户，架构分三步演进。

第一步，服务拆分。把现在的单体 FastAPI 拆成三个独立服务——检索服务（PGVector + ES）、推理服务（Agent + LLM 调用）、对话管理服务（Memory + SSE）。拆分的好处是各服务独立扩缩容：检索负载高就加检索实例，推理负载高就加推理实例，不会互相拖累。

第二步，存储升级。PGVector 单机十万级向量够用，千个企业百万到千万级向量——上 PGVector 读写分离（主库写入、从库查询）或者升级到 Milvus 分布式集群做纯向量检索。ES 同样——单节点升级到多节点集群，按 tenant_id 做索引分片。

第三步，接入层。前端加 CDN，API 层加负载均衡（SLB/ALB），Gateway 做租户路由和限流。SSE 长连接用独立连接管理服务——长连接不能走普通 HTTP 负载均衡，需要支持 sticky session。

多租户隔离：数据层每个 chunk 带 tenant_id，查询时 SQL/ES 过滤。为什么不用独立数据库？千个租户各自建库建 index 管理复杂度爆炸。字段隔离 + 计算资源分级（大客户独立实例、小客户共享）是更务实的方案。

### 第 52 题：为什么同时用 PostgreSQL、PGVector、Elasticsearch、MongoDB？各自的边界在哪？

**回答方式**

四个存储各司其职，逐一说明选择理由和如果不用会怎样。注意 PGVector 是 PG 的扩展，两者是一体的。

**回答**

四个存储各司其职，不是重复建设。

PostgreSQL：业务数据存储——用户、角色、权限、文档元信息、会话记录、运营数据。ACID 事务、成熟的 ORM 支持，传统业务数据的最佳选择。

PGVector：向量存储和语义检索。跟 PostgreSQL 是同一个数据库实例（PGVector 是 PG 的扩展），一条 SQL 能同时做字段过滤和向量相似度检索。这就是选 PGVector 而不是独立 Milvus 的核心原因——不需要维护两套数据库。PG + PGVector 实际是一体的，真正独立运维的只有 PG/ES/MongoDB 三套。

Elasticsearch：关键词检索和全文搜索。IK 分词做中文倒排索引，BM25 做相关性排序。PG 也有全文检索（tsvector），但中文分词和相关性排序远不如 ES 成熟，这块不能省。

MongoDB：配送区域地理数据（仅在蔬蔬买菜项目）。存 GeoJSON 格式配送范围多边形，用 2dsphere 做"点在不在配送区域"查询。MySQL 空间索引也支持但当时 5.7 版本不完善，MongoDB GeoJSON 原生支持更好。

总结：没一个数据库能同时做好 ACID 事务、向量检索、中文全文搜索、地理空间查询——所以选了四个方向最专业的工具。

### 第 53 题：ETL 是同步还是异步？用的什么任务队列？处理失败怎么重试？

**回答方式**

**回答**

### 第 54 题：文档更新了怎么同步到向量库？增量还是全量重建？

**回答方式**

**回答**

## 十四、Java 核心原理（4 题）

### 第 57 题：HashMap 底层原理——put 和 get 的流程、扩容机制、为什么线程不安全？

**回答方式**

按 put 流程走一遍——hash 计算 -> 定位桶 -> 插入/链表/红黑树。再讲扩容机制（resize 的触发条件和过程）。最后说为什么线程不安全（死循环和数据丢失）。

**回答**

HashMap 底层是数组 + 链表 + 红黑树（JDK 8+）。

put 的流程：先算 key 的 hashCode，再高位异或降低哈希碰撞概率（hash = h ^ (h >>> 16)），然后 (n - 1) & hash 定位到桶下标。如果桶为空直接放，不为空就遍历链表——找到相同 key 就覆盖 value，找不到就尾插法追加。当链表长度 >= 8 且数组长度 >= 64 时，链表转红黑树。

get 的流程类似：算 hash -> 定位桶 -> 比较 key 的 equals -> 找到返回 value，找不到返回 null。

扩容机制：默认初始容量 16，负载因子 0.75。当元素数量 > capacity * loadFactor 时触发扩容，容量翻倍。扩容时会重新计算每个元素在新数组中的位置（rehash），因为 (n-1) & hash 里 n 变了。JDK 8 优化了 rehash——元素在新数组中的下标要么不变，要么是“原下标 + 原容量”，不需要重新算 hash。

为什么线程不安全：JDK 7 多线程 put 时并发扩容可能产生环形链表，导致下次 get 死循环。JDK 8 改成了尾插法解决了死循环问题，但多线程 put 仍然可能覆盖数据——两个线程同时判断桶为空，都往里放，后放的覆盖先放的。多线程场景用 ConcurrentHashMap。

### 第 58 题：ConcurrentHashMap 如何保证线程安全？

**回答方式**

分版本说。JDK 7 的分段锁 Segment 和 JDK 8 的 CAS + synchronized 各自优缺点。重点讲 JDK 8 的实现。

**回答**

JDK 7 的 ConcurrentHashMap 用分段锁（Segment 数组），每个 Segment 继承 ReentrantLock，写操作只锁对应 Segment，读操作不加锁（val 用 volatile 保证可见性）。默认 16 个 Segment，最多 16 个线程并发写。缺点是分段粒度偏粗，扩容时每个 Segment 独立扩容。

JDK 8 改成了 CAS + synchronized 锁单个桶。put 流程：先算 hash。桶为空用 CAS 插入，不用加锁。桶不为空用 synchronized 锁住链表/红黑树的头节点，然后遍历插入。扩容支持多线程协助（transfer 方法分片迁移）。并发度比 JDK 7 更高。

size 计算：JDK 8 用 baseCount + CounterCell 数组，先尝试 CAS 更新 baseCount，冲突了就累加到 CounterCell 里。sum 时把 baseCount 和所有 CounterCell 加起来。

读操作全程不加锁——Node 的 val 和 next 都用 volatile 修饰，保证读线程能立即看到写线程的变更。

### 第 60 题：JVM 内存区域和 OOM 排查

**回答方式**

先画 JVM 内存结构（堆、栈、方法区等），再说 OOM 发生在哪些区域，最后讲排查工具和步骤。

**回答**

JVM 运行时数据区分五块。

堆（Heap）：存放对象实例，所有线程共享。分新生代（Eden + Survivor）和老年代。OOM 最常见的区域——java.lang.OutOfMemoryError: Java heap space。

元空间（Metaspace）：类元信息，替换了 JDK 7 的方法区（PermGen），默认受本机内存限制。OOM 报错 Metaspace。

虚拟机栈（Stack）：每个线程私有，存放栈帧（局部变量表、操作数栈、方法出口）。递归过深报 StackOverflowError。

程序计数器（PC）：线程私有，指向当前执行的字节码行号。本地方法栈：执行 native 方法。

OOM 排查步骤：第一步，拿到堆 dump（-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path）。第二步，用 MAT（Memory Analyzer Tool）或 JProfiler 分析——看 Dominator Tree 哪个对象占内存最大、看 GC Roots 引用链找到泄漏点。第三步，结合业务代码判断——是内存泄漏还是内存不足。

常见内存泄漏：静态集合类持有对象引用（static List 不断 add）、未关闭的连接（JDBC、IO 流）、ThreadLocal 使用后没 remove、内部类持有外部类引用导致外部类无法回收。


## 十五、数据库与中间件深度（3 题）

### 第 61 题：MySQL 事务隔离级别和 MVCC 原理

**回答方式**

从四种隔离级别讲到 MVCC 解决的问题（读写不阻塞）。MVCC 讲三个核心概念——隐藏字段、undo log 版本链、ReadView。最后举 RR 级别下间隙锁辅助解决幻读。

**回答**

这个问题我在蔬蔬买菜项目里真实遇到过。运营后台有一个报表查询，同一时间跑两次查出来的数据不一样，排查下来发现是事务隔离级别的问题。MySQL InnoDB 默认是 RR 级别，但我们的报表查询只需要已提交的数据，所以改成了 RC 级别。理解 MVCC 就是解决这个问题的关键。

四种隔离级别：读未提交（脏读、不可重复读、幻读都有）-> 读已提交 RC（解决了脏读，有不可重复读和幻读）-> 可重复读 RR（解决了脏读和不可重复读，InnoDB 默认，间隙锁辅助解决幻读）-> 可串行化（全解决但性能差）。

MVCC 解决的问题：读不加锁，写不阻塞读。核心机制依赖三个东西。

隐藏字段：InnoDB 每行数据有两个隐藏列——DB_TRX_ID（最近修改该行的事务 ID）、DB_ROLL_PTR（指向 undo log 中该行上一个版本的指针）。

undo log 版本链：每次 update 或 delete 把旧版本写入 undo log，通过 DB_ROLL_PTR 串联成一条版本链。

ReadView：事务执行快照读时生成的一个视图，记录当前活跃事务 ID 列表。如果行记录的 DB_TRX_ID 小于 ReadView 的最小活跃 ID，已提交可见。如果在活跃列表里，顺着版本链找上一个版本。

RC 和 RR 的区别：RC 每次 SELECT 都生成新的 ReadView，所以不可重复读。RR 只在第一次 SELECT 时生成 ReadView，后续复用，所以可重复读。

RR 级别下幻读：MVCC 快照读（SELECT）不产生幻读——新插入的行在同一 ReadView 里不可见。但当前读（SELECT ... FOR UPDATE）会幻读——靠间隙锁 gap lock 锁住范围内的间隙，阻止其他事务插入新行。


### 第 62 题：Redis 缓存穿透、击穿、雪崩的区别和解决方案

**回答方式**

三个概念各讲本质 + 场景 + 解决方案，不要混在一起说。最后讲缓存一致性的保证方式。

**回答**

缓存穿透：查询的数据在缓存和数据库中都不存在，每次请求都穿透到数据库。解决方案：一是缓存空结果（空值也缓存，TTL 设短些），二是布隆过滤器（Bloom Filter）——请求来了先判断 key 是否在过滤器中，不在就直接返回。

缓存击穿：一个热点 key 在缓存过期瞬间，大量并发请求同时打到底层数据库。解决方案：一是热点 key 不过期（物理不过期，后台异步更新），二是互斥锁（SETNX 分布式锁）。

缓存雪崩：短时间内大量缓存同时过期，或者 Redis 服务不可用，所有请求直接打到数据库。解决方案：缓存过期时间加随机值避免同时过期；Redis 高可用（主从 + 哨兵 / Cluster）；本地缓存兜底（Guava Cache / Caffeine）。

缓存一致性：先更新数据库，再删除缓存（Cache Aside Pattern）。为什么先删缓存后更新数据库会出现不一致——A 删缓存、B 读缓存发现没有查旧数据写回缓存、A 更新数据库，缓存里是旧数据。先更新数据库再删缓存可以避免，但删除可能失败——配合 Canal 监听 binlog 异步重试删除。

**追问：Redis 和 MySQL 数据不一致到底怎么解决？**

**回答方式**

先说不一致产生的根本原因（并发读写 + 操作顺序），再讲 Cache Aside Pattern 为什么是主流方案，最后补充延时双删和 Canal binlog 订阅两种增强手段。

**回答**

不一致的本质就一句话：数据库和缓存是两个独立的存储，双写时没有一个原子操作可以同时更新两者。只要不是原子操作，就一定会出现“一个成功一个失败”的时间窗口，在这个窗口里读到的就是不一致数据。

主流方案是 Cache Aside Pattern：读的时候先读缓存，没有就读数据库再回写缓存。写的时候先更新数据库，再删除缓存。

为什么是删除缓存而不是更新缓存？因为更新缓存成本更高——如果写操作频繁而读操作不频繁，更新缓存等于做无用功，而且并发写场景下容易出现“后写的缓存覆盖了先写的数据库”的问题。删除缓存只在下次读请求时才按需回填，更简单可靠。

先更新数据库再删缓存这个顺序是经过考量的。如果反过来——先删缓存再更新数据库——会有典型的不一致场景：线程 A 删完缓存，线程 B 读缓存没查到，从数据库读出旧数据写回缓存，然后线程 A 才更新数据库。结果缓存里永远是旧数据。先更新数据库再删缓存可以避免这个问题。但删除缓存这一步本身可能失败——Redis 超时、网络闪断——缓存就永远留着旧数据了。

针对删除失败的场景，有两个增强方案。

第一个是延时双删（Delayed Double Delete）：先删除缓存，再更新数据库，延迟几百毫秒后再删除一次缓存。第二次删除是为了兜住第一次删除到更新数据库之间那个时间窗口里可能回写的旧缓存。但这个方案不优雅——延迟时间设多少不好确定，而且第二次删除还是可能失败。

第二个是 Canal 订阅 binlog 异步删除：先更新数据库（这是唯一可靠的写操作），MySQL 的 binlog 会记录这次变更。Canal 伪装成 MySQL 从库订阅 binlog，解析出变更的 key，发送到消息队列。消费端从 MQ 拿到 key 后执行缓存删除，删除失败可以重试。这套方案的好处是缓存删除和业务代码完全解耦——业务代码只操作数据库，缓存一致性由 Canal + MQ 这个旁路系统保证。缺点是架构复杂，引入了 Canal、MQ 两个新组件，小项目不值得。

日常项目实践中，大部分场景用 Cache Aside Pattern + 删除重试就够了。只有对一致性要求极高的场景（如订单状态、库存数量）才需要上 Canal 方案。无论哪种方案，都要接受最终一致性——Redis 和 MySQL 做不到强一致，只能做到“最终一致”，目标是把不一致的时间窗口缩到最短。


### 第 63 题：消息队列——怎么保证消息不丢失、不重复消费、顺序消费？

**回答方式**

从生产端、存储端、消费端三个维度讲可靠性。

**回答**

坦率说，蔬蔬买菜项目当时没有用消息队列，因为业务量级没到需要异步削峰的程度。但后来在做架构设计时我深入了解了这个选型。

选型：电商项目一般用 RocketMQ 或 RabbitMQ。RocketMQ 适合大规模分布式、事务消息、顺序消息；RabbitMQ 轻量、社区生态好、适合中小规模。

消息不丢失：三端保证。生产端：同步发送 + 确认机制，失败重试。Broker 端：持久化——同步刷盘保证消息写入磁盘才返回。多副本——主从同步复制。消费端：先处理业务逻辑，后手动 ack——业务成功才 ack，失败重回队列。

不重复消费：消费端做幂等——用业务唯一键（如订单号）做去重表。每次消费前先查去重表，有则跳过，无则执行并写入。

顺序消费：RocketMQ 的顺序消息——发送端把同一业务 key 的消息发到同一个 MessageQueue，消费端用 MessageListenerOrderly 单线程消费。代价是并发度降低，只对需要顺序的消息启用。


## 十六、微服务与分布式（2 题）

### 第 64 题：CAP 理论——为什么微服务选了 Nacos 而不是 Eureka？

**回答方式**

先说 CAP 定义（一致性、可用性、分区容错性），再说 Nacos 和 Eureka 的选择，最后结合业务场景说选型考量。

**回答**

CAP 理论：分布式系统中，在必须容忍网络分区（P）的前提下，一致性和可用性只能二选一。

CP 系统：保证强一致性但牺牲部分可用性（ZooKeeper、Nacos CP 模式）。AP 系统：保证可用性但允许最终一致性（Eureka、Nacos AP 模式）。

### 第 65 题：Seata 分布式事务原理——AT 模式和 TCC 模式有什么区别？

**回答方式**

先说 AT 模式的两阶段提交流程（自动生成回滚 SQL），再说 TCC 模式的业务侵入性和优势，最后给选型建议。

**回答**

Seata 核心角色：TC（事务协调器，独立服务）、TM（事务管理器，应用端发起提交/回滚）、RM（资源管理器，管理分支事务）。

AT 模式：Seata 自动代理数据源，对业务代码透明。一阶段：执行业务 SQL，Seata 生成前置镜像和后置镜像，写入 undo log，注册分支事务到 TC。二阶段提交：删除 undo log。二阶段回滚：用前置镜像恢复数据。优点：业务零侵入。缺点：全局锁性能开销。

TCC 模式：业务代码自己实现 Try、Confirm、Cancel 三个方法。Try 检查资源并预留，Confirm 真正扣减，Cancel 释放预留资源。优点：性能好（没有全局锁）。缺点：业务侵入性强，每个方法写三套逻辑。

选型：业务简单追求快速落地用 AT。对性能敏感、愿意投入开发资源用 TCC。电商下单扣库存这种短事务 AT 就够了。


## 十七、系统设计（1 题）

### 第 66 题：如何设计一个短链接系统？

**回答方式**

按“场景分析 -> 核心功能 -> 算法选型 -> 存储设计 -> 高可用”的顺序讲。

**回答**

场景分析：用户输入长链接 -> 系统生成短码（短链接）-> 用户访问短链接时 302 重定向到长链接。核心指标是写入 QPS（不高）和读取 QPS（很高）。

短码生成三种方案：哈希截断（MD5 取前 6 位，有碰撞风险）、发号器（全局自增 ID + 62 进制转换，ID 连续易被恶意遍历）、预生成随机短码（无规律不可预测）。一般选发号器或预生成随机码。

存储：短码和长链接映射用 MySQL。高并发读加 Redis 缓存——先查缓存，未命中再查数据库并回填。缓存 TTL 设长一些，因为映射关系几乎不变化。

重定向：用 302（临时重定向）。301 浏览器会缓存，减少服务端压力但无法统计点击量。302 每次请求到服务器，可以做点击分析。

高可用：发号器不能单点——部署多个实例，每个负责不同的 ID 段，用数据库或 ZooKeeper 分配段。Redis 集群 + 主从。MySQL 读写分离。


## 十八、Spring 核心原理（4 题）

### 第 67 题：Spring IoC 容器原理——BeanFactory 和 ApplicationContext 的区别？

**回答方式**

先说 IoC 的核心思想（控制反转：对象的创建和管理交给容器），再说 BeanFactory 和 ApplicationContext 的继承关系和各自定位。

**回答**

IoC（Inversion of Control，控制反转）就是把对象的创建、组装、管理的控制权从代码中转移给 Spring 容器。开发者只需要定义 Bean 和依赖关系，容器负责实例化和注入。

虽然 IoC 是 Spring 的基础概念，但我真正加深理解是在一次启动排查中——项目启动很慢，怀疑是不是 Bean 加载太多了。排查过程中才发现 ApplicationContext 默认是预加载所有单例 Bean 的，如果换用 BeanFactory 的懒加载策略能解决，但代价是第一次请求慢。这件事让我理解了为什么实际项目里都用 ApplicationContext。

BeanFactory 是 Spring IoC 的顶层接口，提供了最基本的 IoC 功能。它采用懒加载策略——调用 getBean() 时才对 Bean 进行实例化和依赖注入。优点是启动快、资源占用少，适合资源受限的环境（如移动端）。缺点是第一次调用 getBean() 时会有性能损耗。

ApplicationContext 继承了 BeanFactory，在它基础上增加了更多企业级功能：AOP 支持、事件发布（ApplicationEvent）、国际化（MessageSource）、资源加载（ResourceLoader）。它采用预加载策略——容器启动时就会实例化所有单例 Bean。优点是应用启动后访问速度快，缺点是大项目启动慢。

实际开发中几乎不会直接用 BeanFactory，都是用的 ApplicationContext 的各种实现（ClassPathXmlApplicationContext、AnnotationConfigApplicationContext）。Spring Boot 启动时创建的是 AnnotationConfigApplicationContext。

### 第 68 题：Spring Bean 的生命周期

**回答方式**

按阶段讲：实例化 -> 属性赋值 -> 初始化 -> 销毁。初始化阶段重点讲 Aware 接口、BeanPostProcessor、InitializingBean 和 @PostConstruct 的执行顺序。

**回答**

Bean 的生命周期理论上学的时候觉得抽象，但在 KnowOcean 项目中真的用上了。我们有个需求——系统启动后自动把热门文档预加载到缓存。我实现了一个 ApplicationRunner 的 Bean，在启动后执行预热逻辑。但如果用 @PostConstruct，是在 Bean 初始化阶段执行的，那时候有些依赖还没准备好。理解 Bean 的生命周期就知道该选哪个时机。

Spring Bean 的完整生命周期分四个阶段。

第一阶段，实例化：通过反射创建 Bean 实例，类似于 new 了一个空对象。

第二阶段，属性赋值：Spring 根据依赖注入配置（@Autowired、@Resource、XML 配置）为 Bean 填充属性值，包括对其他 Bean 的引用。

第三阶段，初始化。这一步是面试重点，有明确的执行顺序：
1. 调用各种 Aware 接口的方法——BeanNameAware（setBeanName）、BeanFactoryAware（setBeanFactory）、ApplicationContextAware（setApplicationContext）
2. BeanPostProcessor 的 postProcessBeforeInitialization 方法
3. @PostConstruct 注解的方法（JSR-250 规范）
4. InitializingBean 接口的 afterPropertiesSet() 方法
5. init-method（@Bean 的 initMethod 属性）
6. BeanPostProcessor 的 postProcessAfterInitialization 方法（AOP 动态代理就是在这里完成的）

第四阶段，销毁。容器关闭时执行：先 @PreDestroy，再 DisposableBean 的 destroy()，最后 destroy-method。

### 第 69 题：@Transactional 哪些场景会失效？

**回答方式**

先说事务管理的基本原理（AOP 代理），再列出最常见的几种失效场景，每种说清楚为什么。

**回答**

这个我踩过坑。在蔬蔬买菜的下单接口里，一个方法调同一个 Service 类的另一个事务方法，事务没生效，导致数据库写入了不一致的数据。查了半天才发现是同类调用不走代理的问题。后来把那个方法拆到另一个 Service 里就好了。

@Transactional 失效的根本原因是 Spring 的事务管理基于 AOP 代理。当调用不经过代理对象时，事务就不生效。常见的失效场景：

第一，同类方法调用。同一个类中的 A 方法（有 @Transactional）调用 B 方法（也有 @Transactional），B 的事务不会生效。因为调用走的是 this 引用，不是代理对象。解决办法：注入自己的代理（@Autowired 当前类），或者把 B 方法移到另一个 Service 里。

第二，方法不是 public。@Transactional 默认只对 public 方法生效。private、protected、default 方法上的事务注解会被忽略。这是 Spring 的设计决策——CGLIB 和 JDK 动态代理都不能拦截非 public 方法。

第三，异常类型不对。默认情况下只有 RuntimeException（运行时异常）才会回滚，checked exception（Exception 的子类但不是 RuntimeException）不会回滚。因为 Spring 认为 checked exception 是业务预期内的，不需要回滚。解决办法：rollbackFor = Exception.class 覆盖默认策略。

第四，异常被 catch 了。方法内用 try-catch 捕获了异常但没有重新抛出，Spring 收不到异常信号，误以为事务执行成功。解决办法：catch 后要么重新抛出，要么手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。

第五，传播行为配置错误。比如 REQUIRES_NEW 的嵌套事务，内层事务回滚不会影响外层事务。外层事务捕获异常后继续提交，出现"部分失败部分成功"的假象。

### 第 70 题：Spring Boot 自动配置原理

**回答方式**

从 @SpringBootApplication 注解讲起，拆成三个组成注解说清楚。重点讲 @EnableAutoConfiguration → spring.factories → @Conditional 这个链路。

**回答**

自动配置这一点我的理解是从一个 Bug 开始的。有一次项目启动报了 DataSource 相关的错误，但我根本没配数据源——debug 后发现是引入了某个 starter 依赖，它触发了自动配置。这让我去看了 spring.factories 和 @ConditionalOnClass 的机制，理解了自动配置是"按需生效"而不是"全量加载"。

@SpringBootApplication 是一个组合注解，核心由三个注解组成：

@SpringBootConfiguration：本质是 @Configuration，标记当前类是配置类。

@ComponentScan：扫描当前类所在包及其子包中的 @Component 及其派生注解（@Service、@Repository、@Controller）。

@EnableAutoConfiguration：自动配置的核心注解。它通过 @Import(AutoConfigurationImportSelector.class) 导入了一个选择器，这个选择器会去读取 META-INF/spring.factories 文件中所有 EnableAutoConfiguration 的配置项。spring-boot-autoconfigure 包里的 spring.factories 文件定义了上百个自动配置类。

但实际应用启动时不会全部加载。每个自动配置类上都有 @Conditional 系列注解做条件判断——@ConditionalOnClass（类路径有指定类才加载）、@ConditionalOnMissingBean（容器中没有指定 Bean 才加载）、@ConditionalOnProperty（配置文件中指定属性才加载）。比如 DataSourceAutoConfiguration 的条件是类路径下有 DataSource.class 且容器中没有自定义的 DataSource Bean。

这就是为什么在 pom.xml 里加一个 spring-boot-starter-web 依赖，Spring Boot 就能自动配置好 Tomcat 和 DispatchServlet——starter 依赖引入了相关 jar，@ConditionalOnClass 发现类存在，自动配置生效。用户也可以通过配置项或自定义 Bean 覆盖自动配置。



## 十九、MyBatis 与数据库深度（3 题）

### 第 71 题：MyBatis 一二级缓存的区别和问题

**回答方式**

先讲 MyBatis 缓存的分层结构，再说一级缓存和二级缓存的区别、默认行为、以及各自的坑。

**回答**

MyBatis 的一级缓存我碰到过一个坑。在同一个事务里两次查询同一张表，第二次查出来的数据不是最新的，因为另一个线程在中间更新了数据。当时很奇怪为什么数据库已经变了但查出来还是旧的，排查后才发现是一级缓存导致的。所以我对 MyBatis 缓存的态度是：理解它的机制，但生产环境尽量别依赖它，用 Redis 做业务缓存更可控。

MyBatis 的缓存分两级。一级缓存是 SqlSession 级别的，二级缓存是 SqlSessionFactory 级别的。

一级缓存默认开启，同一个 SqlSession 中执行两次相同的查询，第二次直接从缓存拿，不再查数据库。一级缓存的生命周期和 SqlSession 绑定——SqlSession close 或 clearCache 后缓存失效。问题在于，如果 SqlSession 执行了 insert、update、delete 操作，一级缓存会被清空。如果是多表联查，另一个 SqlSession 更新了数据，当前 SqlSession 的一级缓存不会感知，就会出现脏读。所以一级缓存只适合"同一个 SqlSession 内、同一事务、无其他线程并发"的场景。

二级缓存可以跨 SqlSession 共享，但需要手动开启。具体操作：在 Mapper XML 中加 <cache> 标签，实体类实现 Serializable。命中过程：先从二级缓存查，没有再到一级缓存查，没有再查数据库。二级缓存的问题更严重——多表联查时，如果某个 Mapper 开启了二级缓存，而其他 Mapper 改了关联表的数据，缓存不会同步，必出脏数据。所以实际上生产环境里二级缓存默认是关闭的，大部分团队也会强制关掉它。MyBatis-Plus 也是同样的策略。

但实际项目中，90% 的场景不需要 MyBatis 的二级缓存。性能瓶颈在数据库层面的，用 Redis 做业务缓存是更可控的方案。MyBatis 的缓存粒度太粗、失效不可控。

### 第 72 题：MySQL EXPLAIN 怎么看？常见索引失效场景有哪些？

**回答方式**

先用一条重点讲 EXPLAIN 的 type 和 Extra 两个字段怎么看，再列出最常见的 5 种索引失效场景，每句话配一个简单例子。

**回答**

EXPLAIN 输出中最重要的两个字段：type 和 Extra。

type 表示访问类型，从好到差排序：system > const > eq_ref > ref > range > index > ALL。const 是主键或唯一索引查询，性能最好。ref 是普通索引的等值查询。range 是索引范围查询（> < between in）。index 是扫描整个索引树。ALL 是全表扫描，最差。

Extra 常见的：Using index（覆盖索引，不回表）、Using where（在存储引擎层过滤后还在 Server 层过滤）、Using filesort（无法利用索引排序，额外排序操作）、Using temporary（使用了临时表，常见于 group by 和 distinct）、Using index condition（索引下推）。

五种常见索引失效场景：

第一，最左前缀法则。联合索引 (a, b, c)，查询条件必须从索引最左列开始。只查 b 或只查 c 都用不上索引。跳过中间列也会导致后面列的索引失效——where a=? and c=? 只有 a 能用到索引，c 不能。

第二，模糊查询前导通配符。where name like “%张” 或 “%张%”，前导 % 让索引失效。但 “张%” 可以用到索引。

第三，索引列做了计算或函数操作。where SUBSTR(phone, 1, 3) = “138” 或 where salary * 1.2 > 10000，都对索引列做了函数或计算，索引失效。应该在值的这边操作：where phone LIKE “138%”。

第四，索引列类型不匹配。phone 列是 varchar 但查询条件传了数值 where phone = 13812345678，MySQL 会做隐式类型转换，对索引列应用 CAST 函数，索引失效。

第五，or 条件。where a = 1 or b = 2，如果 a 有索引但 b 没有，MySQL 可能选择全表扫描。应该改成两个查询 union all，或者给 b 也加上索引。

### 第 73 题：分库分表策略和大表 DDL 怎么做？

**回答方式**

分库分表先说场景指标（什么时候该分），再说策略（垂直 / 水平、分片键怎么选），最后说大表 DDL 的 Online 方案。

**回答**

坦率说，蔬蔬买菜的项目体量并没有到需要分库分表的程度——订单表几百万行，索引优化后性能是够的。但我在做技术方案时调研过这个方向，为了面试我也系统整理过。

分库分表的核心驱动力是：单表数据量超过千万级后，B+ 树高度增加，索引维护成本变大，写入和查询性能开始下降。一般建议单表超过 500 万行或 10GB 时考虑分表。

垂直拆分：按业务模块拆到不同数据库（用户库、订单库、商品库）。优点是拆分后职责清晰、各自独立扩缩容。缺点是跨库 JOIN 无法用数据库直接做、分布式事务复杂度增加。

水平拆分：同一条记录分散到多个结构相同的表中。关键问题是分片键的选择——选错了查询不走分片键就全库扫描。常见的分片键是 user_id 或 order_id，因为大部分查询都带这两个字段。取模分片（user_id % 128）实现简单但扩容要重新分布数据。一致性哈希可以减少扩容时的数据迁移量。分页和排序在分库分表后很麻烦——需要各分片查询结果后在应用层归并排序。

大表 DDL：MySQL 5.6 之前的 DDL（ALTER TABLE）会锁表，对大表影响很大。5.6 之后引入了 Online DDL（ALGORITHM=INPLACE, LOCK=NONE），大部分操作可以在线执行不阻塞读写。但大表 DDL 仍然有主从延迟问题。生产环境中更推荐使用 gh-ost（GitHub 的开源工具）——它通过 binlog 同步创建一个影子表，在影子表上执行 DDL，完成后 rename 替换原表。整个过程对业务零影响，可以暂停、可以回滚。

实际生产中，不是在日活几千万的场景下，大部分业务单表优化到极致（索引、SQL、硬件）就能扛住，不要轻易上分库分表——引入的复杂度远大于解决的问题。


## 二十、Redis 进阶（2 题）

### 第 74 题：Redis 五种数据结构的底层实现

**回答方式**

从 Redis 对象系统（redisObject）讲起，再说每种数据类型对应的底层编码（ziplist、skiplist、hashtable、intset 等），以及编码转换条件。

**回答**

我们在蔬蔬买菜项目里重度使用了 Redis——用户 Token 用 String、抽奖名单用 Set、热销排行榜用 ZSet。但坦白说，写业务代码时并不需要深入到 SDS 和跳表这个级别。我在一次排查 Redis 内存飙升的问题时，才知道不同数据类型在不同编码方式下内存占用差异巨大，这才去了解了底层实现。

Redis 每个键值对都用一个 redisObject 表示，包含 type（数据类型）和 encoding（底层编码结构）。同一种数据类型可以有不同的底层编码，Redis 会根据数据特征自动选择合适的编码以节省内存。

String：底层用 SDS（Simple Dynamic String），不是 C 的 char[]。SDS 有 len 字段（O(1) 获取长度），有 free 空间预分配（减少内存重分配次数），是二进制安全的（可以存图片等二进制数据）。

List：3.2 之前有两种编码。数据量少时用 ziplist（压缩列表——连续内存块，所有元素挨着存，节省内存），数据量大时转 linkedlist（双向链表）。3.2 之后统一用 quicklist——把 ziplist 作为双向链表的节点，每个节点是一个小的 ziplist，兼顾了内存效率和读写性能。

Hash：数据量少时用 ziplist（键值对挨着存），数据量大时转 hashtable（字典）。转换条件：键或值的长度超过 64 字节，或字段数超过 512 个。

Set：数据量少且元素是整数时用 intset（整数集合，有序紧凑数组），数据量大或有非整数元素时转 hashtable。intset 使用二分查找，查询效率 O(log N)。

ZSet：数据量少时用 ziplist（按 score 顺序排列），数据量大时转 skiplist + hashtable。跳表（skiplist）是多层有序链表，上层可以跨越多个节点快速定位，插入和删除不需要像平衡树那样频繁调整结构。ZSet 用跳表做排序和范围查询，用 hashtable 做单个元素的分值查询（O(1)）。

### 第 75 题：Redis 过期策略和内存淘汰机制

**回答方式**

先说三种过期删除策略和 Redis 实际用的混合方案，再说 8 种内存淘汰策略和选型建议。

**回答**

这个知识点来自一次线上问题——我们在 Redis 里存了一批带过期时间的 Session Token，但发现 Redis 内存不断上涨，过期时间到了也没有释放。排查后才知道 Redis 的过期删除不是实时的，而是定期扫描 + 惰性删除的组合。如果写入了大量带过期时间的 key 但很少访问到，惰性删除就不起作用了。

Redis 删除过期 key 有三种策略。定时删除：为每个过期 key 设置定时器，到期立即删除。优点是对内存最友好，缺点是会大量占用 CPU 时间，Redis 是单线程的，性能无法接受。惰性删除：每次访问 key 时检查是否过期，过期就删除。优点是不额外消耗 CPU，缺点是过期 key 如果一直不被访问就永远占着内存。定期删除：每隔一段时间（默认 100ms）随机抽取一批设置了过期时间的 key，检查并删除过期的。如果过期 key 超过 25% 就继续抽。

Redis 实际用的是惰性删除 + 定期删除的混合方案。定期删除控制 CPU 开销，惰性删除兜住漏网之鱼。但如果写请求远大于删除速度，Redis 内存会持续增长触达上限。这时就触发内存淘汰策略。

Redis 8 种内存淘汰策略（maxmemory-policy）：

noeviction（默认）：不淘汰，写请求直接返回 OOM 错误。最不推荐。

针对设置了过期时间的 key：volatile-lru（淘汰最近最少使用的）、volatile-lfu（淘汰最不经常使用的，4.0 新增）、volatile-ttl（淘汰剩余 TTL 最短的）、volatile-random（随机淘汰）。

针对所有 key：allkeys-lru（淘汰最近最少使用的）、allkeys-lfu（淘汰最不经常使用的）、allkeys-random（随机淘汰）。

生产建议：如果业务有明确的热点数据，用 allkeys-lru 或 allkeys-lfu。如果所有 key 被访问的概率差不多，用 allkeys-random。如果缓存的数据量远超 Redis 内存容量，用 volatile-lru + 设置了过期时间的 key，优先淘汰没设置过期时间的关键数据。


## 二十一、设计模式（2 题）

### 第 76 题：你项目中用了哪些设计模式？

**回答方式**

结合两个项目的具体场景讲——一个场景对应一个模式，说清楚"什么场景 + 怎么用的 + 好处是什么"。不要背定义。

**回答**

在 KnowOcean 项目里用了三个比较明显的设计模式。

第一个是工厂模式。文档解析器要根据文档类型选择不同的解析方法——PDF 解析用 PyMuPDF、Markdown 解析用正则 + 语法树、Word 解析用 python-docx。我定义了一个 DocumentParserFactory，根据文档扩展名返回对应的 Parser 实例。新增一种文档格式只需要加一个新的 Parser 类和注册逻辑，不需要改调用方代码。

第二个是策略模式。RRF 融合排序之后，需要对不同质量等级的检索结果做不同处理。SUFFICIENT 等级的走正常生成，PARTIAL 等级的加免责声明，WEAK 等级的降级为无法回答，NONE 的直接拒答。我定义了 EvidenceHandler 策略接口，每种等级对应一个实现。如果后续新增等级或调整行为，新增一个策略类就行。

第三个是模板方法模式。ETL 流水线统一流程是固定的——解析 -> 清洗 -> 切块 -> 向量化 -> 入库。但不同文档类型在每个步骤的具体实现不同。在抽象的 ETLPipeline 类中定义 execute 骨架方法，子类覆盖各自步骤的实现。

在蔬蔬买菜项目中，策略模式也用到了——支付渠道的处理。微信支付、支付宝、余额支付各自实现 PaymentStrategy 接口，下单时根据支付类型选择对应的策略。避免了大量的 if-else 或 switch-case。

### 第 77 题：Spring 框架中用到了哪些设计模式？

**回答方式**

列举 Spring 最核心的几个设计模式，不用全部列，要说"在 Spring 的哪个地方体现"。

**回答**

Spring 框架本身大量使用了设计模式。

单例模式（Singleton）：Spring IoC 容器中默认创建的 Bean 都是单例的——同一个 Bean 在整个容器中只有一个实例，所有注入的地方共享同一个对象。这也是 Spring 默认的 scope。

工厂模式（Factory）：BeanFactory 本身就是工厂模式的体现，ApplicationContext 是更强大的工厂。通过 getBean() 传入 Bean 名称就能获取对应的实例，调用方不需要关心 Bean 是怎么创建的。

代理模式（Proxy）：Spring AOP 就是基于代理模式实现的。运行时为目标对象创建代理对象，在代理对象的方法调用前后插入增强逻辑。JDK 动态代理（基于接口）和 CGLIB 代理（基于类继承）两种实现方式。

模板方法模式（Template Method）：JdbcTemplate、RestTemplate、RedisTemplate 都是模板方法模式的体现。模板方法定义了固定的流程骨架（如 JdbcTemplate 的 execute 方法定义了"获取连接 -> 创建 Statement -> 执行 SQL -> 处理结果集 -> 关闭资源"），子类通过回调接口提供具体实现（如 RowMapper）。

观察者模式（Observer）：Spring 的事件发布机制——ApplicationEventPublisher 发布事件，@EventListener 或 ApplicationListener 监听事件。发布者和监听者完全解耦。

策略模式（Strategy）：ResourceLoader 根据不同资源路径前缀返回不同的 Resource 实现——classpath: 返回 ClassPathResource、file: 返回 FileSystemResource、http: 返回 UrlResource。


## 二十二、Docker 与部署（1 题）

### 第 78 题：Dockerfile 怎么优化？多阶段构建是什么？

**回答方式**

先说 Dockerfile 常见的优化点（层数、顺序、基础镜像），再讲多阶段构建解决什么问题——构建环境和运行环境分离，重点是有编译步骤的语言。

**回答**

Dockerfile 优化的核心目标是镜像体积小、构建速度快、安全性高。

基础镜像选型：Python 项目用 python:3.11-slim 而不是 python:3.11（减小 800MB 以上）。Java 项目用 eclipse-temurin:17-jre 而不是 jdk 版本（减少一半以上）。alpine 版本可以进一步缩小体积但兼容性问题较多（底层用 musl libc 和 glibc 不完全一致）。

分层和顺序优化：Dockerfile 的每一行都会创建一个新层，层多了镜像大、构建慢。应该把变动频率低的指令放在 Dockerfile 前面（安装系统依赖、安装 pip 包），变动频率高的放后面（COPY 源码）。这样改了源码后只会重建后面的层，前面的层可以直接用缓存。

多阶段构建针对需要编译的语言（Java、Go、C++）特别有用。以 Java 项目为例：第一阶段（build stage）用 maven:3.8-openjdk-17 作为基础镜像，拉取依赖、编译、打包成 jar。第二阶段（run stage）用 eclipse-temurin:17-jre，把第一阶段生成的 jar COPY 过来。这样最终镜像只有 jre 和 jar，没有 maven、没有源码、没有编译中间产物。最终镜像体积从 600MB 左右降到 150MB 左右。


## 二十三、项目深挖（2 题）

### 第 79 题：项目中遇到的最大技术难题是什么？怎么解决的？

**回答方式**

选一个真实的问题，用"“什么场景 -> 出什么问题 -> 排查过程 -> 最终方案 -> 结果如何”"的结构讲。关键是排查过程的思考链，不是最终的答案。

**回答**

我讲 KnowOcean 里的一个典型问题：SSE 连接断开后 Agent 推理任务没有停止，导致后台僵尸任务堆积。

什么场景：用户问了一个复杂问题，Agent 需要多次调用工具（检索 -> 分析 -> 再检索 -> 生成答案），整个过程通过 SSE 流式推送 token。整个过程大约持续 5–10 秒。用户在这个窗口期刷新页面或关闭浏览器时，前端的 EventSource 连接断开，但后端 FastAPI 的 Agent 任务还在执行。

排查：一开始日志里看到一些异常请求超时的报错，结合监控发现服务端并发连接数在某个时间点异常升高。追查后定位到是 SSE 断开时后端没有取消正在执行的 Agent 任务，导致大量已完成但没被消费的响应堆积在内存中。

解决分了四步。第一步，在 SSE 的生成器函数里检测连接的断开状态——每次写 chunk 前检查是否还能写到 response。如果断开则 raise GeneratorExit。第二步，在 Agent 执行循环中加一个“取消令牌”（cancellation token）的检查点——每次工具调用和 LLM 请求后检查令牌状态。第三步，前端的 EventSource 断开时主动发一个 HTTP DELETE 请求通知后端取消指定对话的任务。第四步，后端兜底加超时机制——单个 Agent 执行超过 30 秒自动终止。

结果：僵尸任务堆积问题解决了，服务端并发连接数恢复正常。这个问题的教训是——流式接口和普通接口的边界处理完全不同，SSE 连接断开不等同于任务结束，必须在两端都做取消逻辑。

### 第 80 题：如果重新做一次，你的系统哪个设计会改？

**回答方式**

不要全盘否定自己，选一个你后来意识到不合理的设计，说“当时为什么这么选 + 现在为什么觉得不好 + 如果重做会选什么”。展现成长性思维。

**回答**

我会重新考虑 LangChain 的使用方式。项目初期选了 LangChain 是为了快速搭起 MVP，实际上也的确省了很多样板代码。但中后期 LangChain 的抽象边界越来越不合适——它把 Agent 的整个执行流程封装成了一个黑盒，我们想做自定义的“证据评估”逻辑时发现需要绕过很多层才能侵入到它的流程里。
